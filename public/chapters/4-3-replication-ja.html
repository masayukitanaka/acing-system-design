データベースをスケール（つまり、データベース用語で一般にノードと呼ばれる複数のホスト上に分散データベースを実装）するには、レプリケーション、パーティショニング、シャーディングを通じて行います。レプリケーションはレプリカと呼ばれるデータのコピーを作り、異なるノードに格納することです。パーティショニングとシャーディングはどちらもデータセットをサブセットに分割することに関するものです。シャーディングはサブセットが複数のノードにまたがって分散されることを意味しますが、パーティショニングはそうではありません。単一ホストには制限があるため、要件を満たせません:

  • フォールトトレランス—各ノードはノードやネットワーク障害に備えて、データセンター内および跨いで他のノードにデータをバックアップできます。失敗したノードの役割やパーティション/シャードを他のノードが引き継ぐためのフェイルオーバープロセスを定義できます。
  • より高いストレージ容量—単一ノードを垂直スケールして、最大容量のハードドライブを複数搭載することは可能ですが、金銭的に高くつき、また途中でノードのスループットが問題になることがあります。
  • より高いスループット—データベースは複数の同時プロセスとユーザーに対する読み取りと書き込みを処理する必要があります。垂直スケーリングは、最速のネットワークカード、より良いCPU、より多くのメモリで限界に達します。
  • より低いレイテンシ—レプリカを地理的に分散して、分散したユーザーに近づけることができます。そのデータに対する読み取りがその地域から多い場合、データセンター上の特定のレプリカの数を増やすことができます。

読み取り（SELECT操作）をスケールするには、単純にそのデータのレプリカ数を増やします。書き込みのスケーリングはより難しく、本章の大部分は書き込み操作のスケーリングの難しさへの対処に関するものです。

4.3.1 レプリカの分散

典型的な設計は、同じラック上のホストへ1つのバックアップと、別のラックやデータセンターまたはその両方のホストへ1つのバックアップを置くことです。このトピックには多くの文献があります（例: https://learn.microsoft.com/en-us/azure/availability-zones/az-overview）。

データはシャード化することもでき、それは次の利点を提供します。シャーディングの主なトレードオフは、シャードの場所を追跡する必要があることによる複雑さの増加です:

  • ストレージのスケール—データベース/テーブルが単一ノードに収まらないほど大きい場合、ノード間のシャーディングによりデータベース/テーブルは単一の論理ユニットのままでいられます。
  • メモリのスケール—データベースがメモリに格納される場合、単一ノード上のメモリの垂直スケーリングはすぐに金銭的に高くつくので、シャード化する必要があるかもしれません。
  • 処理のスケール—シャード化されたデータベースは並列処理を活用できます。
  • 局所性—特定のクラスタノードが必要とするデータが、別のノード上の別のシャードではなくローカルに格納される可能性が高いように、データベースをシャード化できます。

注 線形化可能性のために、HDFSのような特定のパーティション化されたデータベースは、削除を追記操作（論理ソフト削除と呼ばれる）として実装します。HDFSではこれをトゥームストーンの追加と呼びます。これにより、削除発生時にまだ実行中の読み取り操作への中断と不整合が防止されます。

4.3.2 シングルリーダーレプリケーション

シングルリーダーレプリケーションでは、すべての書き込み操作がリーダーと呼ばれる単一ノード上で発生します。シングルリーダーレプリケーションは、書き込みではなく読み取りをスケールするためのものです。MySQLやPostgresなどの一部のSQLディストリビューションには、シングルリーダーレプリケーションの設定があります。SQLサービスはACID一貫性を失います。これは、高トラフィックのサービスを提供するためにSQLデータベースを水平スケールすることを選択する場合に関連する考慮事項です。

図4.1はプライマリ・セカンダリリーダーフェイルオーバーを伴うシングルリーダーレプリケーションを示しています。すべての書き込み（SQLでは Data Manipulation Language または DDLクエリとも呼ばれる）はプライマリリーダーノードで発生し、セカンダリリーダーを含むそのフォロワーにレプリケーションされます。プライマリリーダーが故障した場合、フェイルオーバープロセスはセカンダリリーダーをプライマリに昇格させます。故障したリーダーが復旧すると、セカンダリリーダーになります。

図4.1 プライマリ・セカンダリリーダーフェイルオーバーを伴うシングルリーダーレプリケーション。図はArtur Ejsmontの Web Scalability for Startup Engineers、figure 5.4（McGraw Hill, 2015）から引用・改変。

単一ノードには、そのフォロワーが共有しなければならない最大スループットがあり、これがフォロワーの最大数を課し、その結果読み取りスケーラビリティを制限します。さらに読み取りをスケールするには、図4.2に示すようなマルチレベルレプリケーションを使えます。ピラミッドのようにフォロワーの複数のレベルがあります。各レベルは下のレベルにレプリケーションします。各ノードは自分が処理できるフォロワー数にレプリケーションし、一貫性がさらに遅れるというトレードオフがあります。

図4.2 マルチレベルレプリケーション。各ノードはそのフォロワーにレプリケーションし、フォロワーは順番にそのフォロワーにレプリケーションする。このアーキテクチャは、各ノードが処理できるフォロワー数にレプリケーションすることを保証するが、一貫性がさらに遅れるというトレードオフがある。

シングルリーダーレプリケーションは実装が最もシンプルです。シングルリーダーレプリケーションの主な制限は、データベース全体が単一ホストに収まる必要があることです。もう一つの制限は結果整合性で、フォロワーへの書き込みレプリケーションには時間がかかります。

MySQL binlogベースのレプリケーションはシングルリーダーレプリケーションの例です。良い議論についてはEjsmontの本 Web Scalability for Startup Engineers の第5章を参照してください。関連するオンラインドキュメント:

シングルリーダーレプリケーションをスケーリングするハック: アプリケーション層でのクエリロジック

手動で入力された文字列はデータベースサイズをゆっくり増加させ、これは単純な見積もりと計算で検証できます。データがプログラマティックに生成された場合や長期にわたって蓄積された場合、ストレージサイズは単一ノードを超えて成長することがあります。

データベースサイズを減らせないがSQLを使い続けたい場合、可能な方法はデータを複数のSQLデータベース間で分割することです。これは、サービスが複数のSQLデータベースに接続するよう設定される必要があり、アプリケーションのSQLクエリを書き直して適切なデータベースからクエリする必要があることを意味します。

単一のテーブルを2つ以上のデータベースに分割する必要がある場合、アプリケーションは複数のデータベースをクエリして結果を結合する必要があります。クエリロジックはもはやデータベースにカプセル化されておらず、アプリケーションにこぼれ出ています。アプリケーションは、どのデータベースに特定のデータが含まれるかを追跡するためのメタデータを格納しなければなりません。これは本質的に、アプリケーションでのメタデータ管理を伴うマルチリーダーレプリケーションです。サービスとデータベースは保守がより難しくなります。特に、これらのデータベースを使う複数のサービスがある場合は。

例えば、ベーグルカフェのレコメンダー Beigel が毎日数十億の検索を処理する場合、検索を記録する単一のSQLテーブル fact_searches は数日でTB単位に成長します。このデータを複数のデータベース間で分割でき、それぞれが独自のクラスタにあります。日ごとにパーティション化して毎日新しいテーブルを作成し、fact_searches_YYYY_MM_DD の形式（例: fact_searches_2023_01_01 および fact_searches_2023_01_02）でテーブルに名前を付けることができます。これらのテーブルをクエリするどんなアプリケーションもこのパーティションロジック、この場合はテーブル命名規則を持つ必要があります。より複雑な例では、特定の顧客が非常に多くのトランザクションを行うため、彼らだけのテーブルが必要になるかもしれません。検索APIへの多くのクエリが他の食事レコメンダーアプリから発生している場合、それぞれのテーブルを作成できます（例: fact_searches_a_2023_01_01）。これは2023年1月1日のAで始まる会社からのすべての検索を格納するためです。Beigelに検索リクエストを行う会社についてのメタデータを格納する別のSQLテーブル search_orgs が必要になるかもしれません。

これは議論中に可能性として提案できますが、この設計を使う可能性は非常に低いです。マルチリーダーまたはリーダーレスレプリケーションのデータベースを使うべきです。

4.3.3 マルチリーダーレプリケーション

マルチリーダーとリーダーレスレプリケーションは、書き込みとデータベースのストレージサイズをスケールする技法です。これらは、シングルリーダーレプリケーションには存在しない競合状態（レースコンディション）の処理を必要とします。

マルチリーダーレプリケーションでは、その名の通り、リーダーとして指定された複数のノードがあり、書き込みは任意のリーダーで行うことができます。各リーダーは他のすべてのノードに書き込みをレプリケーションしなければなりません。

一貫性の問題とアプローチ

このレプリケーションは、順序が重要な操作に対して一貫性と競合状態を導入します。例えば、ある行が一方のリーダーで更新されているときに、もう一方で削除されている場合、結果はどうあるべきでしょうか? タイムスタンプを使って操作を順序付けることは機能しません。なぜなら異なるノードのクロックは完全に同期できないからです。異なるノードで同じクロックを使おうとしても機能しません。各ノードはクロックの信号を異なる時間に受信するからで、これはクロックスキューと呼ばれるよく知られた現象です。同じソースと定期的に同期されるサーバークロックでも、数ミリ秒以上の差があります。この差より小さい時間間隔で異なるサーバーにクエリが行われる場合、それらが行われた順序を決定することは不可能です。

ここでは、システムデザイン面接で一般的に遭遇する一貫性に関連するレプリケーションの問題とシナリオを議論します。これらの状況は、データベースやファイルシステムを含むあらゆるストレージ形式で発生する可能性があります。Martin Kleppmannの Designing Data-Intensive Applications およびその参考文献には、レプリケーションの落とし穴のより徹底した扱いがあります。

データベースの一貫性の定義は何でしょうか? 一貫性は、データベーストランザクションがデータベースを1つの有効な状態から別の有効な状態へ移行させ、データベースの不変条件を維持することを保証します。データベースに書き込まれるすべてのデータは、制約、カスケード、トリガー、またはそれらの任意の組み合わせを含む、定義されたすべてのルールに従って有効でなければなりません。

本書の他の場所で議論されているように、一貫性は複雑な定義を持ちます。一貫性の一般的な非公式な理解は、データがすべてのユーザーで同じでなければならないというものです:

  1. レプリカが異なる物理サーバー上にあっても、複数のレプリカ上の同じクエリは同じ結果を返すべきです。
  2. 同じ行に影響を与える異なる物理サーバー上のData Manipulation Language（DML）クエリ（つまり INSERT、UPDATE、DELETE）は、送信された順に実行されるべきです。

結果整合性を受け入れるかもしれませんが、特定のユーザーは彼らにとって有効な状態のデータを受け取る必要があるかもしれません。例えば、ユーザーAがカウンターの値をクエリし、カウンターを1増やし、再びそのカウンターの値をクエリする場合、ユーザーAには1増えた値を受け取るのが理にかなっています。一方、カウンターをクエリする他のユーザーには増加前の値が提供されるかもしれません。これはread-after-write一貫性と呼ばれます。

一般的に、一貫性要件を緩和する方法を探してください。すべてのユーザーで一貫性を保たねばならないデータの量を最小化するアプローチを見つけてください。

同じ行に影響を与える異なる物理サーバー上のDMLクエリは競合状態を引き起こす可能性があります。可能な状況:

  • 主キーを持つテーブルの同じ行に対するDELETEとINSERT。DELETEが最初に実行された場合、行が存在するべきです。INSERTが最初の場合、主キーが実行を防ぎ、DELETEが行を削除するべきです。
  • 異なる値での同じセルに対する2つのUPDATE操作。最終状態となるのは1つだけです。

異なるサーバーに同じミリ秒に送信されたDMLクエリはどうでしょうか? これは極めて起こりにくい状況で、そのような状況での競合状態を解決する一般的な慣習はないようです。様々なアプローチを提案できます。一つのアプローチは、DELETEをINSERT/UPDATEより優先し、他のINSERT/UPDATEクエリのタイをランダムに破ることです。とにかく、有能な面接官はこのような信号を生まない議論に50分の面接時間を秒単位で無駄にすることはありません。

4.3.4 リーダーレスレプリケーション

リーダーレスレプリケーションでは、すべてのノードが等しいです。読み取りと書き込みは任意のノードで発生できます。競合状態はどう処理されるか? 一つの方法はクォーラムの概念を導入することです。クォーラムは、コンセンサスのために合意する必要があるノードの最小数です。データベースにnノードがあり、読み取りと書き込みの両方がn/2 + 1ノードのクォーラムを持つ場合、一貫性が保証されると推論するのは簡単です。一貫性を望む場合、速い書き込みと速い読み取りの間で選びます。速い書き込みが必要なら、低い書き込みクォーラムと高い読み取りクォーラムを設定し、速い読み取りには逆を設定します。そうでなければ、結果整合性のみが可能で、UPDATEとDELETE操作は一貫性を保てません。

Cassandra、Dynamo、Riak、Voldemortは、リーダーレスレプリケーションを使うデータベースの例です。Cassandraでは、UPDATE操作は競合状態に苦しみますが、DELETE操作は実際に行が削除される代わりにトゥームストーンを使って実装されます。HDFSでは、読み取りとレプリケーションはラックの局所性に基づいており、すべてのレプリカは等しいです。

4.3.5 HDFSレプリケーション

これはHDFS、Hadoop、Hiveの簡単な復習セクションです。詳細な議論は本書の範囲外です。

HDFSレプリケーションはこれら3つのアプローチのいずれにもきれいに当てはまりません。HDFSクラスタにはアクティブなNameNode、パッシブな（バックアップ）NameNode、複数のDataNodeノードがあります。NameNodeはファイルシステムの名前空間操作（ファイルとディレクトリの開く、閉じる、名前変更）を実行します。また、ブロックからDataNodeへのマッピングも決定します。DataNodeはファイルシステムのクライアントからの読み取り・書き込みリクエストを処理する責任があります。DataNodeはNameNodeからの指示に従ってブロック作成、削除、レプリケーションも実行します。ユーザーデータはNameNodeを通って流れません。HDFSはテーブルをディレクトリ内の1つ以上のファイルとして格納します。各ファイルはブロックに分割され、DataNodeノード間でシャード化されます。デフォルトのブロックサイズは64 MBで、この値は管理者が設定できます。

HadoopはMapReduceプログラミングモデルを使って分散データを格納・処理するフレームワークです。HiveはHadoopの上に構築されたデータウェアハウスソリューションです。Hiveには、効率的なフィルタクエリのために1つ以上のカラムでテーブルをパーティション化する概念があります。例えば、次のようにパーティション化されたHiveテーブルを作成できます:

CREATE TABLE sample_table (user_id STRING, created_date DATE, country STRING) PARTITIONED BY (created_date, country);

図4.3はこのテーブルのディレクトリツリーを示しています。テーブルのディレクトリには日付の値のサブディレクトリがあり、それらは順にカラムの値のサブディレクトリを持ちます。created_dateやcountryでフィルタリングされたクエリは、関連するファイルのみを処理し、フルテーブルスキャンの無駄を回避します。

図4.3 カラムに日付と国を含み、これら2つのカラムでパーティション化された「sample_table」テーブルのHDFSディレクトリツリーの例。sample_tableディレクトリには日付値のサブディレクトリがあり、それらは順にカラム値のサブディレクトリを持つ。（出典: https://stackoverflow.com/questions/44782173/hive-does-hive-support-partitioning-and-bucketing-while-usiing-external-tables.）

HDFSは追記専用で、UPDATEやDELETE操作はサポートしません。UPDATEとDELETEから生じる可能性のあるレプリケーション競合状態のためと思われます。INSERTには競合状態がありません。

HDFSには名前クォータ、容量クォータ、ストレージタイプクォータがあります。ディレクトリツリーに関しては:

  • 名前クォータはファイル名とディレクトリ名の数のハードリミットです。
  • 容量クォータはすべてのファイル内のバイト数のハードリミットです。
  • ストレージタイプクォータは特定のストレージタイプの使用量のハードリミットです。HDFSストレージタイプの議論は本書の範囲外です。

ヒント HadoopとHDFSの初心者はしばしばHadoopのINSERTコマンドを使うが、これは避けるべきです。INSERTクエリは1行だけの新しいファイルを作成し、これは64 MBのブロック全体を占有し、無駄になります。また名前の数にも寄与し、プログラマティックなINSERTクエリはすぐに名前クォータを超えます。詳細については https://hadoop.apache.org/docs/current/hadoop-project-dist/hadoop-hdfs/HdfsQuotaAdminGuide.html を参照してください。HDFSファイルに直接追記するべきで、追記される行が既存の行と同じフィールドを持つようにして、データの不整合や処理エラーを防止します。

HDFSにデータを保存するSparkを使用している場合、代わりに saveAsTable または saveAsTextFile を使うべきです。次のコード例のように。Sparkドキュメント（https://spark.apache.org/docs/latest/sql-data-sources-hive-tables.html）などを参照してください。

val spark = SparkSession.builder().appName("Our app").config("some.config", "value").getOrCreate()

val df = spark.sparkContext.textFile({hdfs_file})

df.createOrReplaceTempView({table_name})

spark.sql({spark_sql_query_with_table_name}).saveAsTextFile({hdfs_directory})

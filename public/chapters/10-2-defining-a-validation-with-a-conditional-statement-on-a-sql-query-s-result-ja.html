用語の明確化：テーブルには行と列があります。特定の（行、列）座標のエントリは、セル、要素、データポイント、または値と呼べます。本章ではこれらの用語を交換可能に使います。

手動で定義された検証を、SQLクエリの結果に対する比較演算子でどう定義できるかを議論しましょう。SQLクエリの結果は2次元配列で、これを「result」と呼びます。resultに対して条件文を定義できます。いくつかの例を見ていきましょう。これらの例はすべて日次検証なので、昨日の行のみを検証し、サンプルクエリにはWHERE句「Date(timestamp) > Curdate() - INTERVAL 1 DAY」が含まれます。各例では、まず検証内容を説明し、続いてそのSQLクエリ、そして可能な条件文を示します。

手動で定義された検証は以下に対して定義できます。

  • 列の個別データポイント―前述した「最新タイムスタンプが24時間未満」が一例です。

SELECT COUNT(*) AS cnt

FROM Transactions

  • WHERE Date(timestamp) >= Curdate() - INTERVAL 1 DAY
  • 真となる可能な条件文はresult[0][0] > 0 およびresult['cnt'][0] > 0です。
  • 別の例を議論しましょう。特定のクーポンコードIDが特定の日付に期限切れになる場合、その日以降にこのコードIDが出現するとアラートを発する定期検証を、transactionsテーブルに対して定義できます。これはクーポンコードIDが誤って記録されている可能性を示し得ます。

SELECT COUNT(*) AS cnt

FROM Transactions

WHERE code_id = @code_id AND Date(timestamp) > @date

  • ➥AND Date(timestamp) = Curdate() - INTERVAL 1 DAY
  • 真となる可能な条件文はresult[0][0] == 0 およびresult['cnt'][0] == 0です。
  • 列の複数データポイント―たとえば、個別のアプリユーザーが1日に5回を超える購入をできない場合、いずれかのユーザーIDが前日以降に5行を超えて存在するときにアラートを発する日次検証を、transactionsテーブルに定義できます。これはバグ、その日にユーザーが誤って5回を超える購入ができたこと、または購入が誤って記録されていることを示し得ます。

SELECT user_id, count(*) AS cnt

FROM Transactions

WHERE Date(timestamp) = Curdate() - INTERVAL 1 DAY

  • GROUP BY user_id
  • 条件文はresult.length <= 5です。
  • 別の可能性：

SELECT *

FROM (

  SELECT user_id, count(*) AS cnt

FROM Transactions

  WHERE Date(timestamp) = Curdate() - INTERVAL 1 DAY

  GROUP BY user_id

) AS yesterday_user_counts

  • WHERE cnt > 5;
  • 条件文はresult.length == 0です。
  • 単一行の複数列―たとえば、特定のクーポンコードを使った売上の合計回数が1日に100を超えてはならない、というケース。

SELECT count(*) AS cnt

FROM Transactions

WHERE Date(timestamp) = Curdate() - INTERVAL 1 DAY

  • ➥AND coupon_code = @coupon_code
  • 条件文はresult.length <= 100です。
  • 別のクエリと条件文の組み合わせは次のとおりです。

SELECT *

FROM (

  SELECT count(*) AS cnt

FROM Transactions

WHERE Date(timestamp) = Curdate() - INTERVAL 1 DAY

➥AND coupon_code = @coupon_code

) AS yesterday_user_counts

  • WHERE cnt > 100;
  • 条件文はresult.length == 0です。
  • 複数テーブル―たとえば、北米の売上を記録するファクトテーブルsales_naがあり、country_code列を持つとします。地域ごとの国コードのリストを持つディメンションテーブルcountry_codesを作成できます。新しい行のcountry_codeの値がすべて北米の国であることを確認する定期検証を定義できます。

SELECT *

FROM sales_na S JOIN country_codes C ON S.country_code = C.id

  • WHERE C.region != 'NA';
  • 条件文はresult.length == 0です。
  • 複数クエリに対する条件文―たとえば、ある日の売上数が前週の同じ曜日と比較して10%以上変化した場合にアラートを発したい場合があります。次のように2つのクエリを実行して結果を比較できます。クエリ結果をresult配列に追加するので、このresult配列は2Dではなく3Dになります。

SELECT COUNT(*)

FROM sales

WHERE Date(timestamp) = Curdate()

SELECT COUNT(*)

FROM sales

  • WHERE Date(timestamp) = Curdate() - INTERVAL 7 DAY

条件文はMath.abs(result[0][0][0] – result[1][0][0]) / result[0][0][0] < 0.1です。

手動で定義する検証には他にも数えきれない可能性があります。たとえば：

  • 1時間あたりテーブルに書き込まれる新しい行数の最小値。
  • 特定の文字列列はnull値を含んではならず、文字列長は1～255の間でなければならない。
  • 特定の文字列列は特定の正規表現にマッチする値でなければならない。
  • 特定の整数列は非負でなければならない。

これらの種類の制約の一部は、Hibernateの@NotNullや@Length(min = 0, max = 255)といったORMライブラリの関数アノテーションや、GolangのSQLパッケージの制約型でも実装できます。この場合、本監査サービスは追加の検証層として機能します。監査の失敗はサービス内のサイレントエラーを示しており、調査すべきです。

本節の例はSQLでした。この概念は、HiveQL、Trino（旧称PrestoSQL）、Sparkといった他のクエリ言語での検証クエリ定義にも一般化できます。本設計はデータベースクエリ言語を使った検証定義に焦点を当てていますが、汎用プログラミング言語での検証関数も定義できます。

本節では、以下の一般的な通信パラダイムを紹介し比較します。サービスのためにパラダイムを選択する際には、トレードオフを考慮すべきです。

  • REST（Representational State Transfer）
  • RPC（Remote Procedure Call）
  • GraphQL
  • WebSocket

6.7.1 OSI（Open Systems Interconnection）参照モデル

6.7.2 REST

読者はREST、すなわちHTTPメソッドとリクエスト／レスポンスのボディ（最も一般的にはJSONまたはXMLでエンコードされる）を用いるステートレス通信アーキテクチャの基本に親しんでいることを前提とします。本書では、APIにはRESTを、POSTリクエストおよびレスポンスのボディにはJSONを使用します。JSONスキーマはJSON Schema組織の仕様（https://json-schema.org/）で表現できますが、本書では行いません。なぜなら、50分のシステム設計面接でJSONスキーマを詳細に議論するには、通常これは冗長すぎて低レベルすぎるためです。

RESTは学習、セットアップ、試行、（curlやRESTクライアントを使った）デバッグが簡単です。その他の利点としては、後述するハイパーメディアおよびキャッシング機能があります。

ハイパーメディア

ハイパーメディアコントロール（HATEOAS）あるいはハイパーメディアとは、レスポンス内で「次に利用可能なアクション」に関する情報をクライアントに提供するという考え方です。これは、レスポンスJSON内の「links」のようなフィールドの形を取り、その中にクライアントが論理的に次に問い合わせ得るAPIエンドポイントが含まれます。

たとえば、eコマースアプリが請求書を表示した後、次のステップはクライアントが支払いを行うことです。請求書エンドポイントのレスポンスボディには、次のように支払いエンドポイントへのリンクが含まれることがあります。

{

  "data": {

    "type": "invoice",

    "id": "abc123",

  },

 

  "links": {

    "pay": "https://api.acme.com/payment/abc123"

  }

}

ここでは、レスポンスには請求書IDが含まれており、次のステップはその請求書IDに対する支払いをPOSTすることです。

また、エンドポイントに関するメタデータ（利用可能なアクション、更新可能なフィールド、特定のフィールドが期待するデータなど）を取得するためのOPTIONS HTTPメソッドもあります。

実務上は、ハイパーメディアやOPTIONSはクライアント開発者にとって使いづらく、各エンドポイントや関数のAPIドキュメントをクライアント開発者に提供する方が理にかなっています。たとえばRESTにはOpenAPI（https://swagger.io/specification/）、あるいはRPCやGraphQLフレームワークの組み込みドキュメントツールを使うのが良いでしょう。

リクエスト／レスポンスのJSONボディ仕様に関する規約については、https://jsonapi.org/ を参照してください。

RPCやGraphQLのような他の通信アーキテクチャはハイパーメディアを提供しません。

キャッシング

開発者は可能な限りRESTリソースをキャッシュ可能と宣言すべきです。これには次のような利点があります。

  • ネットワーク呼び出しの一部を回避できるため、レイテンシが下がる。
  • サービスが利用不能でもリソースが利用可能なため、可用性が高まる。
  • サーバへの負荷が下がるため、スケーラビリティが向上する。

キャッシングにはExpires、Cache-Control、ETag、Last-Modified のHTTPヘッダを使用します。

Expires HTTPヘッダは、キャッシュされたリソースの絶対的な有効期限を指定します。サービスは現在時刻から1年先までの時刻値を設定できます。ヘッダの例はExpires: Mon, 11 Dec 2021 18:00 PST です。

Cache-Control ヘッダは、リクエストおよびレスポンスの双方におけるキャッシュ指示（ディレクティブ）をカンマ区切りで列挙したものです。ヘッダの例はCache-Control: max-age=3600 で、これはレスポンスを3600秒間キャッシュ可能であることを意味します。POSTやPUTリクエストには、サーバにこのデータをキャッシュするよう指示するCache-Control ヘッダを含めることができますが、これはサーバがその指示に従うことを意味するわけではなく、そのデータのレスポンスにこの指示が含まれない場合もあります。すべてのキャッシュリクエスト・レスポンス指示についてはhttps://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control を参照してください。

ETag の値は、リソースの特定のバージョンを識別する不透明な文字列トークンです。（不透明トークン（opaque token）は、発行者だけが知る独自フォーマットを持つトークンです。不透明トークンを検証するには、トークンの受信者がそれを発行したサーバを呼び出す必要があります。）クライアントはGETリクエストにETag の値を含めることで、リソースをより効率的にリフレッシュできます。サーバは、リソースのETag が異なる場合にのみリソースの値を返します。言い換えれば、リソースの値が変化した場合のみ返し、クライアントがすでに持っているのであればリソースの値を不必要に返さないということです。

Last-Modified ヘッダはリソースが最後に変更された日時を含み、ETag ヘッダが利用できない場合のフォールバックとして使えます。関連するヘッダにはIf-Modified-Since とIf-Unmodified-Since があります。

RESTの欠点

RESTの欠点は、ハイパーメディアやOPTIONSエンドポイント以外には統合された文書化の仕組みがないことです（しかも開発者はそれらの提供を見送ることもできます）。RESTフレームワークで実装したサービスには、OpenAPIなどのドキュメントフレームワークを別途追加する必要があります。さもなければ、クライアントは利用可能なリクエストエンドポイントや、そのパス・クエリパラメータ、リクエストおよびレスポンスのボディフィールドといった詳細を知る術がありません。RESTにはまた、標準化されたバージョン管理手順もなく、「/v2」「/v3」のようなパスを使ったバージョン管理が一般的な慣習となっています。もう1つの欠点は、RESTには普遍的な仕様がないため混乱を招くことです。ODataやJSON-APIはよく使われる2つの仕様です。

6.7.3 RPC（Remote Procedure Call）

RPCは、プログラマがネットワークの詳細を扱うことなく、別のアドレス空間（つまり別のホスト）でプロシージャを実行させる手法です。人気のオープンソースRPCフレームワークには、GoogleのgRPC、FacebookのThrift、PythonのRPyCがあります。

面接のためには、次のような一般的なエンコーディング形式に親しんでおくべきです。エンコーディング（シリアライゼーションまたはマーシャリングとも呼ばれる）とデコーディング（パース、デシリアライゼーション、アンマーシャリングとも呼ばれる）の方法を理解しておくべきです。

  • CSV、XML、JSON
  • Thrift
  • Protocol Buffers（protobuf）
  • Avro

gRPCのようなRPCフレームワークがRESTに対して持つ主な利点は次のとおりです。

  • RPCはリソース最適化のために設計されているため、スマートホームデバイスのようなIoTデバイスを含む低電力デバイスにとって最良の通信アーキテクチャ選択肢です。大規模Webサービスにとっては、RESTやGraphQLと比較してリソース消費が少ないことが、スケールに伴って大きな差となります。
  • Protobufは効率的なエンコーディングです。JSONは繰り返しが多く冗長であり、リクエストとレスポンスを大きくします。ネットワークトラフィックの節約は、スケールに伴って大きな効果を生みます。
  • 開発者はエンドポイントのスキーマをファイルに定義します。一般的なフォーマットにはAvro、Thrift、protobufがあります。クライアントはこれらのファイルを用いてリクエストを作成し、レスポンスを解釈します。スキーマのドキュメント化はAPI開発に必須のステップであるため、クライアント開発者は常に良質なAPIドキュメントを持つことになります。これらのエンコーディング形式にはスキーマ変更のルールもあり、スキーマ変更時に後方互換性および／または前方互換性をどう維持するかが開発者にとって明確になります。

RPCの主な欠点もまた、バイナリプロトコルとしての性質に由来します。特に組織外においては、クライアントがスキーマファイルの最新バージョンに追従し続けるのが面倒です。また、組織が内部ネットワークトラフィックを監視したい場合、RPCのようなバイナリプロトコルよりもRESTのようなテキストプロトコルの方が容易です。

6.7.4 GraphQL

GraphQLは宣言的なデータ取得を可能にするクエリ言語で、クライアントはAPIから必要なデータを正確に指定できます。ピンポイントなリクエストのためのAPIデータクエリと操作の言語を提供します。この柔軟性をナビゲートするために不可欠な、統合されたAPIドキュメントツールも提供します。主な利点は次のとおりです。

  • クライアントが必要なデータとその形式を決定する。
  • サーバは効率的で、クライアントが要求した通りに正確に提供する。アンダーフェッチング（複数回のリクエストが必要になる）やオーバーフェッチング（レスポンスサイズが膨張する）が発生しない。

トレードオフ：

  • 単純なAPIには複雑すぎる場合がある。
  • セキュリティの仕組みを含めて、RPCやRESTよりも学習曲線が急である。
  • RPCやRESTよりもユーザーコミュニティが小さい。
  • エンコーディングがJSONのみであり、JSONのトレードオフをすべて引き継ぐ。
  • 各APIユーザーが少しずつ異なるクエリを実行するため、ユーザー分析がより複雑になる場合がある。RESTやRPCでは、各APIエンドポイントに何件のクエリが行われたかを容易に把握できますが、GraphQLではこれが見えにくくなります。
  • 外部APIにGraphQLを使う場合は慎重であるべき。これはデータベースを公開してクライアントにSQLクエリを許すのに似ています。

GraphQLの利点の多くはRESTでも実現できます。単純なAPIは、シンプルなREST HTTPメソッド（GET, POST, PUT, DELETE）とシンプルなJSONボディから始めることができます。要件が複雑になるにつれて、OData https://www.odata.org/のようなRESTのより高度な機能を使ったり、複数のリソースからの関連データを1つのリクエストに結合するためにJSON-APIのhttps://jsonapi.org/format/#fetching-includes 機能を使ったりできます。GraphQLはその機能の標準的な実装とドキュメントを提供するため、複雑な要件に対応するうえではRESTより便利なことがあります。一方、RESTには普遍的な標準はありません。

6.7.5 WebSocket

WebSocketは、永続的なTCP接続上で全二重通信を行うための通信プロトコルです。これはリクエストごとに新しい接続を作成し、レスポンスごとに閉じるHTTPとは異なります。REST、RPC、GraphQL、Actorモデルは設計パターンや思想ですが、WebSocketとHTTPは通信プロトコルです。それでも、WebSocketをAPIのアーキテクチャスタイルとして他と比較することには意味があります。なぜなら、APIを他の4つの選択肢ではなくWebSocketで実装することを選べるからです。

WebSocket接続を作成するには、クライアントがサーバにWebSocketリクエストを送ります。WebSocketは最初の接続を確立するためにHTTPハンドシェイクを使い、サーバにHTTPからWebSocketへのアップグレードを要求します。以降のメッセージは、この永続的なTCP接続上でWebSocketを使用できます。

WebSocketは接続を開いたままにするため、すべての関係者にとってオーバーヘッドが増加します。これは、WebSocketがステートフルである（RESTとHTTPはステートレス）ことを意味します。リクエストは、RESTのようにどのホストでも処理できるのではなく、関連する状態／接続を持つホストによって処理されなければなりません。WebSocketがステートフルである性質と、接続維持のリソースオーバーヘッドの両方により、WebSocketはスケーラビリティに劣ります。

WebSocketはp2p通信を可能にするため、バックエンドが不要です。スケーラビリティを犠牲にして、より低いレイテンシとより高い性能を得るトレードオフです。

6.7.6 比較

面接中に、これらのアーキテクチャスタイル間のトレードオフ、およびスタイルとプロトコルを選択するうえで考慮すべき要因を評価する必要があるかもしれません。RESTとRPCが最も一般的です。スタートアップは通常シンプルさのためにRESTを使う一方、大規模な組織はRPCの効率性や後方・前方互換性の恩恵を受けられます。GraphQLは比較的新しい思想です。WebSocketはp2p通信を含む双方向通信に有用です。その他の参考文献にはhttps://apisyouwonthate.com/blog/picking-api-paradigm/ およびhttps://www.baeldung.com/rest-vs-websockets があります。

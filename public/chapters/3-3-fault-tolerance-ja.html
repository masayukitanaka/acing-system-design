フォールトトレランスとは、一部のコンポーネントが障害を起こしてもシステムが動作し続け、ダウンタイムが発生した場合に永久的な害（データ損失など）を防ぐ能力です。これにより優雅な機能低下が可能になり、システムは一部が障害を起こしたときに完全な壊滅的故障ではなく、ある程度の機能を維持できます。これによりエンジニアは故障した部分を修正してシステムを動作状態に戻す時間を稼げます。また、自動的に置換コンポーネントをプロビジョニングしてシステムに取り付けるセルフヒーリングメカニズムを実装することもでき、システムは手動介入なしで、エンドユーザーに気づかれることなく回復できます。

可用性とフォールトトレランスはしばしば一緒に議論されます。可用性は稼働時間/ダウンタイムの尺度ですが、フォールトトレランスは尺度ではなくシステムの特性です。

密接に関連する概念は障害設計（failure design）で、これは滑らかなエラー処理に関するものです。制御外のサードパーティAPIのエラーや、サイレント/未検出エラーをどう処理するかを検討してください。フォールトトレランスの技法には次のものがあります。

3.3.1 レプリケーションと冗長性

レプリケーションは第4章で議論されます。

一つのレプリケーション技法は、コンポーネントの複数（例えば3つ）の冗長インスタンス/コピーを持つことで、最大2つが同時にダウンしても稼働時間に影響を与えないようにすることです。第4章で議論するように、更新操作は通常特定のホストに割り当てられるので、他のホストがリクエスト元から地理的に離れた異なるデータセンターにある場合のみ更新パフォーマンスに影響しますが、読み取りはしばしばすべてのレプリカで行われるので、コンポーネントがダウンすると読み取りパフォーマンスが低下します。

1つのインスタンスが真実の源（しばしばリーダーと呼ばれる）として指定され、他の2つのコンポーネントはレプリカ（またはフォロワー）として指定されます。レプリカの可能な配置は様々です。1つのレプリカは同じデータセンター内の異なるサーバーラックに、もう1つのレプリカは別のデータセンターにあります。別の配置は、3つすべてのインスタンスを別々のデータセンターに置くことで、低いパフォーマンスとのトレードオフでフォールトトレランスを最大化します。

例として、Hadoop Distributed File System (HDFS) は、任意のブロックのコピー数を設定するための「レプリケーション係数」と呼ばれる設定可能なプロパティを持ちます。デフォルト値は3です。レプリケーションは可用性の向上にも役立ちます。

3.3.2 前方誤り訂正と誤り訂正符号

前方誤り訂正（FEC）は、誤り訂正符号（ECC）を使うなどして、メッセージを冗長な方法でエンコードすることで、ノイズや信頼できない通信チャネル上のデータ伝送のエラーを防ぐ技法です。

FECはシステムレベルというよりプロトコルレベルの概念です。システムデザイン面接中にFECとECCについての認識を示すことができますが、詳細に説明する必要はおそらくないので、本書ではこれ以上議論しません。

3.3.3 サーキットブレーカー

サーキットブレーカーは、クライアントが障害を起こす可能性が高い操作を繰り返し試みるのを止めるメカニズムです。下流サービスに関して、サーキットブレーカーは最近の間隔内に失敗したリクエスト数を計算します。エラー閾値を超えると、クライアントは下流サービスの呼び出しを止めます。その後しばらくして、クライアントは限定された数のリクエストを試みます。成功した場合、クライアントは障害が解決されたと仮定し、制限なしでリクエストの送信を再開します。

定義 サービスBがサービスAに依存している場合、Aは上流サービス、Bは下流サービスです。

サーキットブレーカーは、失敗する可能性が高いリクエストに費やされるリソースを節約します。また、すでに過負荷のシステムにさらなる負担を加えるクライアントを防ぎます。

しかし、サーキットブレーカーはシステムのテストを困難にします。例えば、不正確なリクエストを行っているがシステムの限界を適切にテストしている負荷テストがあるとします。このテストはサーキットブレーカーを作動させ、以前は下流サービスを圧倒していたかもしれない負荷が今では通ってしまうことになります。顧客による同様の負荷は停止を引き起こすでしょう。適切なエラー閾値とタイマーを推定することも困難です。

サーキットブレーカーはサーバー側で実装できます。例はResilience4j（https://github.com/resilience4j/resilience4j）です。これはNetflixで開発され2017年にメンテナンスモードに移行したHystrix（https://github.com/Netflix/Hystrix、https://github.com/Netflix/Hystrix/issues/1876#issuecomment-440065505）に触発されました。Netflixの焦点は、事前設定された設定よりもむしろアプリケーションのリアルタイムパフォーマンスに反応するより適応的な実装、例えば適応的並行性制限（https://netflixtechblog.medium.com/performance-under-load-3e6fa9a60581）の方へ移行しました。

3.3.4 指数バックオフとリトライ

指数バックオフとリトライはサーキットブレーカーに似ています。クライアントがエラーレスポンスを受け取ると、リクエストを再試行する前に待ち、リトライ間の待機時間を指数的に増加させます。クライアントはまた、待機期間を「ジッター」と呼ばれる技法で小さなランダムな正または負の量で調整します。これにより、複数のクライアントが正確に同じ時刻にリトライを送信することを防ぎ、下流サービスを圧倒する「リトライストーム」を引き起こすことを防ぎます。サーキットブレーカーと同様、クライアントが成功レスポンスを受信すると、障害が解決したと仮定し、制限なしでリクエスト送信を再開します。

3.3.5 他サービスのレスポンスのキャッシング

私たちのサービスは、特定のデータについて外部サービスに依存することがあります。外部サービスが利用できない場合をどう扱うべきか? 一般に、クラッシュしたりエラーを返したりするより、優雅な機能低下の方が望ましいです。戻り値の代わりにデフォルトまたは空のレスポンスを使えます。古いデータを使う方がデータなしより良い場合は、成功したリクエストを行うたびに外部サービスのレスポンスをキャッシュし、外部サービスが利用できないときにそれらのレスポンスを使えます。

3.3.6 チェックポインティング

マシンは、多くのデータポイントに対して、サブセットを体系的に取得し、それに集約を実行し、結果を指定された場所に書き込み、すべてのデータポイントが処理されるまで、またはストリーミングパイプラインの場合のように無限にこのプロセスを繰り返すことで、特定のデータ集約操作を実行することがあります。データ集約中にこのマシンが故障した場合、置換マシンは集約を再開すべきデータポイントを知っている必要があります。これは、各データポイントのサブセットが処理されて結果が正常に書き込まれた後にチェックポイントを書き込むことで実現できます。置換マシンはチェックポイントから処理を再開できます。

チェックポインティングはKafkaのようなメッセージブローカーを使うETLパイプラインに一般的に適用されます。マシンはKafkaトピックからいくつかのイベントを取得し、イベントを処理し、結果を書き込んだ後にチェックポイントを書きます。このマシンが故障した場合、置換マシンは最新のチェックポイントから再開できます。

KafkaはKafka内でパーティションレベルのオフセットストレージを提供します（https://kafka.apache.org/22/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html）。FlinkはKafkaトピックからデータを消費し、Flinkの分散チェックポインティングメカニズムを使って定期的にチェックポイントを取ります（https://ci.apache.org/projects/flink/flink-docs-master/docs/dev/datastream/fault-tolerance/checkpointing/）。

3.3.7 デッドレターキュー

サードパーティAPIへの書き込みリクエストが失敗した場合、リクエストをデッドレターキューにキューイングし、後でリクエストを再試行できます。

デッドレターキューはローカルに格納されるのか別のサービスに格納されるのか? 複雑さと信頼性をトレードオフできます:

  • 最もシンプルな選択肢は、リクエストの欠落が許容される場合、失敗したリクエストを単に破棄することです。
  • try-catchブロックでデッドレターキューをローカルに実装する。ホストが故障するとリクエストが失われます。
  • より複雑で信頼性の高い選択肢は、Kafkaのようなイベントストリーミングプラットフォームを使うことです。

面接では、複数のアプローチとそのトレードオフを議論すべきです。1つのアプローチだけを述べてはいけません。

3.3.8 ロギングと定期的な監査

サイレントエラーを処理する一つの方法は、書き込みリクエストをログに記録し、定期的な監査を実行することです。監査ジョブはログを処理し、書き込み先のサービスのデータが期待値と一致することを検証できます。これは第10章でさらに議論します。

3.3.9 バルクヘッド

バルクヘッドパターンはフォールトトレランスメカニズムで、システムが隔離されたプールに分割されるので、1つのプールでの故障がシステム全体に影響しないようにします。

例えば、サービスの様々なエンドポイントがそれぞれ独自のスレッドプールを持ち、スレッドプールを共有しないようにすると、あるエンドポイントのスレッドプールが枯渇しても、他のエンドポイントがリクエストを処理する能力には影響しません（詳細についてはIndrasiriとSiriwardena著の Microservices for the Enterprise: Designing, Developing, and Deploying （Apress, 2019）を参照してください。）

バルクヘッドのもう一つの例は、Michael T. Nygardの Release It!: Design and Deploy Production-Ready Software, Second Edition （Pragmatic Bookshelf, 2018）で議論されています。バグのため特定のリクエストがホストをクラッシュさせる原因になるかもしれません。このリクエストが繰り返されるたびに、別のホストがクラッシュします。サービスをバルクヘッドに分割（つまりホストをプールに分割）すると、このリクエストがすべてのホストをクラッシュさせて全面停止を引き起こすのを防げます。このリクエストは調査されるべきなので、サービスにはロギングとモニタリングが必要です。モニタリングは問題のリクエストを検出し、エンジニアはログを使ってクラッシュをトラブルシュートし原因を特定できます。

あるいは、リクエスト発行者がサービスへの高いリクエストレートを持ち、サービスが他のリクエスト発行者にサービスを提供できなくなる場合もあります。バルクヘッドパターンは特定のリクエスト発行者に特定のホストを割り当て、リクエスト発行者がサービスの容量をすべて消費するのを防ぎます。（第8章で議論するレートリミットも、この状況を防ぐ別の方法です。）

サービスのホストはプールに分割でき、各プールはリクエスト発行者に割り当てられます。これは、特定のリクエスト発行者により多くのリソースを割り当てることで、それらを優先する技法でもあります。

図3.1では、1つのサービスが他の2つのサービスにサービスを提供しています。そのサービスのホストが利用できなくなると、どのリクエスト発行者にもサービスを提供できなくなります。

図3.1 サービス0へのすべてのリクエストはそのホスト間でロードバランスされる。サービス0のホストが利用できなくなると、どのリクエスト発行者にもサービスを提供できなくなる。

図3.2では、サービスのホストがプールに分割され、リクエスト発行者に割り当てられています。1つのプールのホストが利用できなくなっても、他のリクエスト発行者には影響しません。このアプローチの明らかなトレードオフは、特定のリクエスト発行者からのトラフィックスパイクがあった場合に、プールが互いを支援できないことです。これは特定のリクエスト発行者に特定のホスト数を割り当てるために行った意図的な決定です。必要に応じてプールを手動または自動でスケールできます。

図3.2 サービス0は2つのプールに分割され、それぞれがリクエスト発行者に割り当てられている。1つのプールが利用できなくなっても、もう1つには影響しない。

バルクヘッドパターンの他の例については、Michael Nygardの本 Release It!: Design and Deploy Production-Ready Software, Second Edition（Pragmatic Bookshelf, 2018）を参照してください。

パート2のシステム設計の議論ではバルクヘッドに言及しませんが、ほとんどのシステムに一般的に適用可能で、面接中に議論できます。

3.3.10 フォールバックパターン

フォールバックパターンは、問題を検出し、その後代替コードパス（クライアントが情報を取得しようとしているサービスに類似したキャッシュされたレスポンスや代替サービスなど）を実行することで構成されます。例えば、クライアントが近くのベーグルカフェのリストをバックエンドにリクエストする場合、バックエンドサービスが停止中であれば将来使われるレスポンスをキャッシュできます。このキャッシュされたレスポンスは最新ではないかもしれませんが、ユーザーにエラーメッセージを返すよりは良いです。代替案は、クライアントがBingやGoogle MapsのようなサードパーティのマップAPIにリクエストを行うことですが、これらは私たちのバックエンドが提供するカスタマイズされたコンテンツを持っていないかもしれません。フォールバックを設計するときは、その信頼性と、フォールバック自体が失敗する可能性を考慮すべきです。

注 フォールバック戦略、Amazonがフォールバックパターンをほとんど使わない理由、Amazonが使うフォールバックパターンの代替案については、https://aws.amazon.com/builders-library/avoiding-fallback-in-distributed-systems/を参照してください。

図7.1の下部の図は、より従来型の高レベルアーキテクチャを示しています。UIフロントエンドサービスがバックエンドサービスとオブジェクトストアサービスにリクエストを行います。バックエンドサービスはSQLサービスにリクエストを行います。

このアプローチでは、オブジェクトストアは画像ファイル用であり、SQLデータベースは7.4節で議論したように投稿の残りのデータを格納します。すべてのデータを画像も含めてSQLデータベースに格納し、オブジェクトストアをまったく持たないこともできました。しかしそうすると、クライアントは画像ファイルをバックエンドホスト経由でダウンロードしなければなりません。これはバックエンドホストへの追加負荷となり、画像ダウンロードのレイテンシを増加させ、突発的なネットワーク接続問題によるダウンロード失敗の可能性も全体として高めます。

初期実装をシンプルに保ちたい場合は、投稿に画像を載せる機能なしで進め、その機能を実装したくなったときにオブジェクトストアを追加することも検討できます。

そうは言っても、各投稿は1 MBの画像ファイル最大10枚に制限されており、大きな画像ファイルを格納するわけではないので、この要件が将来変わる可能性があるかを面接官と議論できます。より大きな画像が必要にならなさそうであれば、画像をSQLに格納することを提案できます。imageテーブルにはpost_idテキスト列とimageブロブ列を持たせられます。この設計の利点はシンプルさです。

ここまでは、ユーザーのリクエストレートがリクエストのタイムスタンプによって決定されると仮定してきましたが、リクエストレートを計算する可能な手法については実際には議論していませんでした。ここで主な問いの1つは、分散レート制限サービスがリクエスト元の現在のリクエストレートをどう判定するかです。一般的なレート制限アルゴリズムには次のようなものがあります。

  • Token bucket（トークンバケット）
  • Leaky bucket（リーキーバケット）
  • Fixed window counter（固定ウィンドウカウンタ）
  • Sliding window log（スライディングウィンドウログ）
  • Sliding window counter（スライディングウィンドウカウンタ）

先に進む前に、システム設計面接の問題のなかには、ほとんどの候補者が事前経験を持たないであろう専門的な知識や経験を必要とするように見えるものがあることに留意します。面接官は候補者がレート制限アルゴリズムに親しんでいることを期待していないかもしれません。これは、候補者のコミュニケーション能力と学習能力を評価するための機会となります。面接官は私たちにレート制限アルゴリズムを説明し、要件を満たすソリューションをそのアルゴリズムを軸に共同で設計する能力を評価することもあり得ます。

面接官は大胆な一般化や誤った発言をすることさえあり、それらを批判的に評価し、機転を利かせながら、毅然と、明確かつ簡潔に賢明な質問を投げかけ、技術的な意見を表明する能力を評価することもあります。

サービスに複数のレート制限アルゴリズムを実装し、本サービスの各ユーザーが要件に最も近いアルゴリズムを選べるようにすることも検討できます。このアプローチでは、ユーザーは所望のアルゴリズムを選び、Rulesサービスで所望の設定を行います。

議論の単純化のため、本節のレート制限アルゴリズムの議論は、レート制限が10秒間で10リクエストであると仮定します。

8.9.1 Token bucket

図8.12を参照すると、トークンバケットアルゴリズムはトークンで満たされたバケツのアナロジーに基づいています。バケツには3つの特徴があります。

  • トークンの最大数。
  • 現在利用可能なトークンの数。
  • バケツにトークンが追加される補充レート。

図8.12 1秒に1回エンキューするトークンバケット

リクエストが届くたびに、バケツからトークンを1つ取り除きます。トークンがなければ、リクエストは拒否されるかレート制限されます。バケツは一定レートで補充されます。

このアルゴリズムの素直な実装では、各ユーザーリクエストに対して次のことが起こります。ホストはハッシュマップを使ってキーバリューペアを格納できます。ホストがこのユーザーIDのキーを持っていない場合、システムはユーザーIDとトークン数9（10–1）のエントリを初期化します。ホストがこのユーザーIDのキーを持ち、値が0より大きい場合は、システムはその値をデクリメントします。カウントが0なら、true、すなわちユーザーをレート制限すべきと返します。falseを返した場合は、ユーザーをレート制限しません。システムは、10未満であれば毎秒すべての値を1ずつ増やす必要もあります。

トークンバケットの利点は、理解と実装が容易で、メモリ効率が良いこと（各ユーザーはトークン数をカウントするための単一の整数変数だけで済む）です。

この実装で明らかに考慮すべき点は、各ホストがハッシュマップ内のすべてのキーをインクリメントする必要があることです。ホストのメモリ上のハッシュマップでは実現可能です。Redisデータベースのようにホスト外部にストレージがある場合、Redisは複数のキーを更新するMSET（https://redis.io/commands/mset/）コマンドを提供していますが、単一MSET操作で更新できるキー数に制限がある可能性があります（https://stackoverflow.com/questions/49361876/mset-over-400-000-map-entries-in-redis）。（Stack Overflowは学術的に信頼できる情報源ではなく、MSETに関する公式Redisドキュメントには1リクエストあたりのキー数の上限は記載されていません。しかし、システムを設計する際は常に妥当な質問を行うべきであり、公式ドキュメントすら完全に信頼すべきではありません。）さらに、各キーが64ビットなら、1,000万キーを更新するリクエストは8.08 GBのサイズとなり、大きすぎます。

更新コマンドを複数のリクエストに分割する必要があれば、各リクエストはリソースオーバーヘッドとネットワークレイテンシを発生させます。

さらに、キーを削除する仕組み（直近リクエストを行っていないユーザーを除去する仕組み）がないため、トークン補充リクエストレートを減らすためや、直近リクエストを行ったユーザーのためにRedisデータベースの空きを作るために、いつユーザーを除去するかをシステムは知りません。システムはユーザーリクエストの最終タイムスタンプを記録する別のストレージメカニズムと、古いキーを削除するプロセスが必要になります。

8.8節のような分散実装では、各ホストが自身のトークンバケットを持ち、それを使ってレート制限判定を下す場合があります。ホストは8.8.2節で議論した手法でバケットを同期するかもしれません。あるホストが他のホストとバケットを同期する前に、自身のバケットを使ってレート制限判定を下すと、ユーザーは設定したレート制限より高いレートでリクエストを行えてしまう可能性があります。たとえば、2つのホストがそれぞれ近い時間にリクエストを受け取ると、各々がトークンを1つ減らして9トークン残り、その後他のホストと同期します。リクエストが2回あったにも関わらず、全ホストが9トークンに同期されてしまいます。

Cloud Bouncer

2014年にYahooで開発されたCloud Bouncer（https://yahooeng.tumblr.com/post/111288877956/cloud-bouncer-distributed-rate-limiting-at-yahoo）は、トークンバケットに基づく分散レート制限ライブラリの例です。

8.9.2 Leaky bucket

リーキーバケットは、最大トークン数を持ち、一定レートで漏れ（leak）、空になると漏れを止めます。リクエストが届くたびに、バケツにトークンを1つ追加します。バケツが満杯なら、リクエストは拒否されるかレート制限されます。

図8.13を参照すると、リーキーバケットの一般的な実装は、固定サイズのFIFOキューを使うことです。キューは定期的にデキューされます。リクエストが届いたとき、キューに空きがあればトークンをエンキューします。固定サイズのキューのため、この実装はトークンバケットよりメモリ効率が劣ります。

図8.13 1秒に1回デキューするリーキーバケット

このアルゴリズムにはトークンバケットと同じいくつかの問題があります。

  • 毎秒、ホストはすべてのキーのすべてのキューをデキューする必要がある。
  • 古いキーを削除する別の仕組みが必要。
  • キューはその容量を超えられないため、分散実装では、同期前に複数のホストがバケツ／キューを同時にいっぱいまで満たす可能性がある。これはユーザーがレート制限を超えたことを意味する。

もう1つの可能な設計は、トークンではなくタイムスタンプをエンキューすることです。リクエストが届いたら、まずキュー内に残る最古のタイムスタンプが保持期間より新しくなるまでデキューし、その後キューに空きがあればリクエストのタイムスタンプをエンキューします。エンキューが成功すればfalse、そうでなければtrueを返します。このアプローチは、毎秒すべてのキューからデキューする必要をなくします。

問い 考えられる整合性の問題に気付くでしょうか？

注意深い読者は、レート制限判定に不正確さを引き起こす可能性のある2つの整合性問題に即座に気付くでしょう。

  1. あるホストがリーダーホストにキーバリューペアを書き込んだ直後に、別のホストによって即座に上書きされる競合状態が起こり得る。
  2. ホストのクロックが同期されておらず、ホストが他のホストのわずかに異なるクロックで書かれたタイムスタンプを使ってレート制限判定を下す可能性がある。

このわずかな不正確さは許容できます。これら2つの問題は、本節で議論したタイムスタンプを使う他のすべての分散レート制限アルゴリズム、すなわちfixed window counterおよびsliding window logにも当てはまりますが、改めて言及はしません。

8.9.3 Fixed window counter

固定ウィンドウカウンタはキーバリューペアとして実装されます。キーはクライアントIDとタイムスタンプの組み合わせ（例：user0_1628825241）、値はリクエストカウントです。クライアントがリクエストを行うと、キーが存在すればインクリメントされ、なければ作成されます。カウントが設定レート制限内であればリクエストは許可され、レート制限を超えれば拒否されます。

ウィンドウ区間は固定です。たとえば、ウィンドウは毎分の[0, 60)秒の間にできます。ウィンドウが経過した後、すべてのキーが期限切れになります。たとえば、キー「user0_1628825241」は1628825241が3:27:21 AM GMT（3:27 AM GMTの分内）なので、3:27:00 AM GMTから3:27:59 AM GMTまで有効です。

問い リクエストレートは設定レート制限をどれだけ超えうるでしょうか？

固定ウィンドウカウンタの欠点は、設定レート制限の最大2倍までのリクエストレートを許してしまう可能性があることです。たとえば、図8.13を参照し、レート制限が1分間で5リクエストの場合、クライアントは[8:00:00 AM, 8:01:00 AM)で最大5リクエスト、[8:01:00 AM, 8:01:30 AM)でさらに最大5リクエストを行えます。クライアントは実際には1分間隔で10リクエストを行ったことになり、毎分5リクエストという設定レート制限の2倍です（図8.14）。

図8.14 ユーザーは[8:00:30 AM, 8:01:30 AM)で5リクエスト、[8:01:00 AM, 8:01:30 AM)でさらに5リクエストを行った。固定ウィンドウあたり5リクエストという制限内ではあるが、実際には1分間で10リクエストを行った。

このアプローチをレートリミッタに適合させると、ホストがユーザーリクエストを受け取るたびに、ハッシュマップに対して次のステップを実行します。これらのステップのシーケンス図は図8.15を参照してください。

  1. 問い合わせる適切なキーを決定する。たとえば、レート制限が10秒の有効期限を持つ場合、1628825250時点のuser0に対応するキーは[“user0_1628825241”, “user0_1628825242”, …, “user0_1628825250”]となる。
  2. これらのキーへのリクエストを行う。キーバリューペアをホストのメモリではなくRedisに格納している場合、指定したすべてのキーの値を返すMGET（https://redis.io/commands/mget/）コマンドを使える。MGETコマンドは取得するキー数NについてO(N)であるが、複数リクエストではなく単一リクエストを行うことでネットワークレイテンシとリソースオーバーヘッドが低くなる。
  3. キーが見つからない場合は、新しいキーバリューペア（例：(user0_1628825250, 1)）を作成する。1つのキーが見つかった場合は、その値をインクリメントする。複数のキーが見つかった場合（競合状態による）、返されたすべてのキーの値を合計し、その合計を1だけインクリメントする。これが直近10秒のリクエスト数。
  4. 並列で：
  1. 新規または更新したキーバリューペアをリーダーホスト（またはRedisデータベース）に書き込む。複数のキーがあった場合、最も古いものを除いてすべてのキーを削除する。
  2. カウントが10より大きければtrue、そうでなければfalseを返す。

図8.15 固定ウィンドウカウンタアプローチのシーケンス図。この図はRedisの代わりにホストのメモリを使ってリクエストタイムスタンプを格納するアプローチを示しています。レート制限判定は、ホストのメモリに格納されたデータだけを使って、即座にホスト上で行われます。同期のためのリーダーホスト上の後続ステップは図示していません。

問い ステップ5で複数のキーが見つかる原因となる競合状態はどのようなものでしょうか？

Redisのキーは期限切れに設定できる（https://redis.io/commands/expire/）ので、10秒後に期限切れとなるようにキーを設定すべきです。さもないと、期限切れキーを継続的に見つけて削除する別のプロセスを実装する必要があります。このプロセスが必要な場合、キー削除プロセスがホストから独立していることは固定ウィンドウカウンタの利点です。この独立した削除プロセスはホストとは別にスケールでき、独立して開発できるためテストとデバッグが容易になります。

8.9.4 Sliding window log

スライディングウィンドウログは、各クライアントに対するキーバリューペアとして実装されます。キーはクライアントID、値はソートされたタイムスタンプのリストです。スライディングウィンドウログは、各リクエストごとにタイムスタンプを格納します。

図8.16はスライディングウィンドウログのシンプルな図示です。新しいリクエストが入ってきたら、そのタイムスタンプを追加し、最初のタイムスタンプが期限切れかをチェックします。そうであれば、二分探索で最後の期限切れタイムスタンプを見つけ、それより前のすべてのタイムスタンプを削除します。キューは二分探索をサポートしないため、キューではなくリストを使います。リストのサイズが10を超えればtrue、そうでなければfalseを返します。

図8.16 スライディングウィンドウログのシンプルな図示。新しいリクエストが行われたときにタイムスタンプを追加する。次に、二分探索で最後の期限切れタイムスタンプを見つけ、すべての期限切れタイムスタンプを削除する。リストのサイズが上限を超えていなければリクエストは許可される。

スライディングウィンドウログは正確です（ただし分散実装では8.9.2節の最終段落で議論した要因により例外あり）が、各リクエストにタイムスタンプ値を格納するため、トークンバケットよりも多くのメモリを消費します。

スライディングウィンドウログアルゴリズムはレート制限を超えた後もリクエストをカウントするため、ユーザーのリクエストレートを測定することもできます。

8.9.5 Sliding window counter

スライディングウィンドウカウンタは、固定ウィンドウカウンタとスライディングウィンドウログをさらに発展させたものです。複数の固定ウィンドウ区間を使い、各区間はレート制限の時間ウィンドウの1/60th の長さです。

たとえば、レート制限区間が1時間なら、1時間のウィンドウを1つ使う代わりに60個の1分ウィンドウを使います。現在のレートは、直近60ウィンドウを合計して決定されます。リクエストをわずかに少なくカウントする可能性があります。たとえば、11:00:35にリクエストをカウントすると、[10:01:00, 10:01:59]ウィンドウから[11:00:00, 11:00:59]ウィンドウまでの60個の1分ウィンドウを合計し、[10:00:00, 10:00:59]ウィンドウは無視します。このアプローチは依然として固定ウィンドウカウンタよりも正確です。

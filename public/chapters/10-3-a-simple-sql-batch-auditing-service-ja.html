本節ではまず、SQLテーブルを監査するシンプルなスクリプトを議論します。次に、このスクリプトからどうやってバッチ監査ジョブを作成できるかを議論します。

10.3.1 監査スクリプト

バッチ監査ジョブの最もシンプルな形式は、次のステップを実行するスクリプトです。

  1. データベースクエリを実行する
  2. 結果を変数に読み込む
  3. この変数の値を特定の条件と照合する

次のリストにあるPythonスクリプトの例は、transactionsテーブルの最新タイムスタンプが24時間未満であるかをチェックするMySQLクエリを実行し、結果をコンソールに出力します。

リスト10.1 最新タイムスタンプを確認するためのPythonスクリプトとMySQLクエリ

import mysql

cnx = mysql.connector.connect(user='admin', password='password',

                         host='127.0.0.1',

                         database='transactions')

cursor = cnx.cursor()

query = """

SELECT COUNT(*) AS cnt

FROM Transactions

WHERE Date(timestamp) >= Curdate() - INTERVAL 1 DAY

"""

cursor.execute(query)

results = cursor.fetchall()

cursor.close()

cnx.close()

# result[0][0] > 0 is the condition.

print(result[0][0] > 0) # result['cnt'][0] > 0 also works.

複数のデータベースクエリを実行して結果を比較する必要があるかもしれません。リスト10.2は可能な例です。

10.3.2 監査サービス

次に、これをバッチ監査サービスに拡張しましょう。スクリプトを一般化し、ユーザーが以下を指定できるようにできます。

  1. SQLデータベースとクエリ。
  2. クエリ結果に対して実行する条件。

Pythonファイルテンプレートを実装してみましょう。これをvalidation.py.templateと命名できます。リスト10.3はこのファイルの可能な実装です。これは簡略化された実装です。バッチ監査ジョブは2つのフェーズに分けます。

  1. データベースクエリを実行し、その結果から監査の合否を判定する。
  2. 監査が失敗した場合、アラートをトリガーする。

実用的な実装では、ログイン認証情報はシークレット管理サービスから供給され、ホストは設定ファイルから読み取られます。これらの詳細は本問題の範囲外です。本サービスのユーザーストーリーは次のようになります。

  1. ユーザーがサービスにログインし、新しいバッチ監査ジョブを作成する。
  2. ユーザーがデータベース、クエリ、条件の値を入力する。
  3. サービスはこのvalidation.py.templateからvalidation.pyファイルを作成し、{database}のようなパラメータをユーザーの入力値で置き換える。
  4. サービスは新しいAirflowまたはcronジョブを作成し、validation.pyをインポートしてvalidation関数を実行する。

これらのvalidation.pyファイルは本質的に関数であることに気付くでしょう。バッチETLサービスはオブジェクトではなく関数を格納します。

先のvalidation.py.templateでは、データベースクエリごとにAirflowタスクを作成すべきだとコメントしました。バックエンドはそのようなvalidation.pyファイルを生成すべきです。これは良いコーディング面接の演習になりますが、システム設計面接の範囲外です。

リスト10.3 監査サービスのためのPythonファイルテンプレート

from datetime import datetime, timedelta

from airflow import DAG

from airflow.operators.bash import BranchPythonOperator

import mysql.connector

import os

import pdpyras

# Example user inputs:

# {name} – ''

# {queries} – ['', '']

# {condition} – result[0][0][0] result[1][0][0]

def _validation():

  results = []

  # Database queries are expensive. An issue with running every query here

  # is that if a query fails, all queries need to be rerun.

  # We can consider instead creating an Airflow task for each query.

  for query in {queries}:

    cnx = mysql.connector.connect(user='admin', password='password',

                               host='127.0.0.1',

                               database=query['database'])

    cursor = cnx.cursor()

    cursor.execute(query['query'])

  results.append(cursor.fetchall())

  cursor.close()

  cnx.close()

  # XCom is an Airflow feature to share data between tasks.

  ti.xcom_push(key='validation_result_{name}', value={condition})

 

def _alert():

  # Some sample code to trigger a PagerDuty alert if the audit failed.

  # This is just an example and should not be taken as working code.

  # We may also wish to send this result to our Backend Service.

  # This is discussed later in this chapter.

  result = ti.xcom_pull(key='validation_result_{name}')

  if result:

    routing_key = os.environ['PD_API_KEY']

    session = pdpyras.EventsAPISession(routing_key)

    dedup_key = session.trigger("{name} validation failed", "audit")

 

with DAG(

    {name},

    default_args={

       'depends_on_past': False,

       'email': ['zhiyong@beigel.com'],

       'email_on_failure': True,

       'email_on_retry': False,

       'retries': 1,

       'retry_delay': timedelta(minutes=5),

 },

 description={description},

 schedule_interval=timedelta(days=1),

 start_date=datetime(2023, 1, 1),

 catchup=False,

 tags=['validation', {name}],

) as dag:

 t1 = BranchPythonOperator(

     task_id='validation',

     python_callable=_validation

 )

 # Alerting is a separate Airflow task, so in case the alert fails,

 # the Airflow job does not rerun the expensive validation function.

 t2 = BranchPythonOperator(

     task_id='alert',

     python_callable=_alert

 )

 t1 >> t2

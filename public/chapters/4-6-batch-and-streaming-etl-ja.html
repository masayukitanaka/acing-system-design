ETL（Extract, Transform, Load）は、1つ以上のソースから、ソースとは異なる方法でデータを表現する、またはソースとは異なるコンテキストでデータを表現する宛先システムにデータをコピーする一般的な手順です。バッチはデータをバッチで処理することを指し、通常は定期的ですが手動でトリガーすることもできます。ストリーミングは、リアルタイムで処理されるデータの連続的な流れを指します。

バッチ vs. ストリーミングは、ポーリング vs. 割り込みに類似していると考えられます。ポーリングと同様、バッチジョブは処理する新しいイベントがあるかどうかに関係なく定義された頻度で常に実行されるのに対し、ストリーミングジョブはトリガー条件が満たされたとき（通常は新しいイベントの公開時）に実行されます。

バッチジョブのユースケース例は、顧客の月次請求書（PDFまたはCSVファイルなど）を生成することです。このような請求書の生成に必要なデータが毎月特定の日にしか利用できない場合（例: 顧客の請求書を生成するために必要なベンダーからの請求明細）、このようなバッチジョブは特に関連しています。これらの定期的なファイルを生成するためのすべてのデータが組織内で生成される場合、Kappaアーキテクチャ（第17章を参照）を検討し、各データが利用可能になり次第処理するストリーミングジョブを実装できます。このアプローチの利点は、月が終わるとほぼ同時に月次ファイルが利用可能になること、データ処理コストが月全体に分散されること、そしてGB単位のデータを処理するバッチジョブよりも、一度に小さなデータを処理する関数のデバッグが簡単なことです。

AirflowとLuigiは一般的なバッチツールです。KafkaとFlinkは一般的なストリーミングツールです。FlumeとScribeはロギング用の特殊なストリーミングツールで、多くのサーバーからリアルタイムでストリーミングされるログデータを集約します。ここでいくつかのETLの概念を簡単に紹介します。

ETLパイプラインはタスクの有向非巡回グラフ（DAG）で構成されます。DAGでは、ノードがタスクに対応し、その祖先がその依存関係です。ジョブはETLパイプラインの単一の実行です。

4.6.1 シンプルなバッチETLパイプライン

シンプルなバッチETLパイプラインは、crontab、2つのSQLテーブル、各ジョブのスクリプト（つまりスクリプト言語で書かれたプログラム）を使って実装できます。cronは並列性のない小さな非クリティカルなジョブに適しており、単一マシンで十分です。次は2つのSQLテーブルの例です:

CREATE TABLE cron_dag (

  id INT,         -- ジョブのID。

  parent_id INT,        -- 親ジョブ。ジョブは0、1、または複数の親を持てる。

  PRIMARY KEY (id),

  FOREIGN KEY (parent_id) REFERENCES cron_dag (id)

);

CREATE TABLE cron_jobs (

  id INT,

  name VARCHAR(255),

  updated_at INT,

  PRIMARY KEY (id)

);

crontabの指示はスクリプトのリストにできます。この例ではPythonスクリプトを使用しましたが、任意のスクリプト言語を使えます。すべてのスクリプトを共通のディレクトリ /cron_dag/dag/ に置き、他のPythonファイル/モジュールを他のディレクトリに置けます。ファイルの整理方法にルールはありません。これは最良の配置だと信じるものに任せます:

0 * * * * ~/cron_dag/dag/first_node.py

0 * * * * ~/cron_dag/dag/second_node.py

各スクリプトは次のアルゴリズムに従えます。ステップ1と2は再利用可能なモジュールに抽象化できます:

  1. 関連するジョブのupdated_at値が依存ジョブのものより小さいことを確認する。
  2. 必要に応じてモニタリングをトリガーする。
  3. 具体的なジョブを実行する。

このセットアップの主な欠点は:

  • スケーラブルではない。すべてのジョブが単一ホスト上で実行され、これは単一ホストのすべての通常の欠点を伴います:
  • 単一障害点がある。
  • 特定の時刻にスケジュールされたすべてのジョブを実行するための計算リソースが不足するかもしれない。
  • ホストのストレージ容量を超える可能性がある。
  • ジョブは、数百万のデバイスへの通知送信などの多くの小さなタスクで構成される場合があります。そのようなジョブが失敗してリトライが必要な場合、成功した小さなタスクを繰り返さないようにする必要があります（つまり、個々のタスクは冪等であるべき）。このシンプルな設計はそのような冪等性を提供しません。
  • PythonスクリプトとSQLテーブルでジョブIDが一貫していることを確認する検証ツールがないため、このセットアップはプログラミングエラーに対して脆弱です。
  • GUIがない（自分で作らない限り）。
  • まだロギング、モニタリング、アラートを実装していません。これは非常に重要で、次のステップであるべきです。例えば、ジョブが失敗したり、ジョブを実行しているホストがクラッシュしたらどうしますか? スケジュールされたジョブが正常に完了することを保証する必要があります。

質問 このシンプルなバッチETLパイプラインのスケーラビリティと可用性を改善するために、どう水平スケールできますか?

専用のジョブスケジューリングシステムにはAirflowやLuigiが含まれます。これらのツールはDAG可視化のためのWeb UIとGUIのユーザーフレンドリーさを備えています。また垂直スケーラブルで、大量のジョブを管理するためにクラスタ上で実行できます。本書では、バッチETLサービスが必要なときはいつでも、組織レベルの共有Airflowサービスを使います。

4.6.2 メッセージング用語

本節では、技術的な議論や文献で遭遇しがちな様々な種類のメッセージングとストリーミングセットアップの一般的な用語を明確化します。

メッセージングシステム

メッセージングシステムは、アプリケーション間のデータ送信と共有の複雑さを減らすために、あるアプリケーションから別のアプリケーションへデータを転送するシステムの一般的な用語で、これによりアプリケーション開発者はデータ処理に集中できます。

メッセージキュー

メッセージは、あるサービスから別のサービスに送信される命令のワークオブジェクトを含み、処理されるためにキューで待機しています。各メッセージは単一の消費者によって一度だけ処理されます。

プロデューサー/コンシューマー

プロデューサー/コンシューマー（パブリッシャー/サブスクライバー、または pub/sub とも呼ばれる）は、イベントを生成するサービスとイベントを処理するサービスを疎結合にする非同期メッセージングシステムです。プロデューサー/コンシューマーシステムには1つ以上のメッセージキューが含まれます。

メッセージブローカー

メッセージブローカーは、メッセージを送信者の正式なメッセージングプロトコルから受信者の正式なメッセージングプロトコルに変換するプログラムです。メッセージブローカーは変換層です。KafkaとRabbitMQはどちらもメッセージブローカーです。RabbitMQは「最も広く展開されているオープンソースメッセージブローカー」と主張しています（https://www.rabbitmq.com/）。AMQPはRabbitMQが実装するメッセージングプロトコルの一つです。AMQPの説明は本書の範囲外です。Kafkaは独自のカスタムメッセージングプロトコルを実装しています。

イベントストリーミング

イベントストリーミングは、リアルタイムで処理されるイベントの連続的な流れを指す一般的な用語です。イベントは状態変化に関する情報を含みます。Kafkaは最も一般的なイベントストリーミングプラットフォームです。

プル vs. プッシュ

サービス間通信はプルまたはプッシュで行えます。一般的に、プルはプッシュよりも良く、これがプロデューサー・コンシューマーアーキテクチャの背後にある一般的な概念です。プルでは、コンシューマーがメッセージ消費のレートを制御し、過負荷になりません。

負荷テストとストレステストは、開発中にコンシューマーで行え、本番トラフィックでのスループットとパフォーマンスをモニタリングし、テストと比較することで、テストを改善するためにより多くのエンジニアリングリソースが必要かどうかを正確に判断できます。コンシューマーは時間の経過に伴うスループットとプロデューサーキューサイズをモニタリングでき、チームは必要に応じてそれをスケールできます。

本番システムが継続的に高負荷の場合、キューが長時間空になることはなく、コンシューマーはメッセージをポーリングし続けることができます。数分以内に予測不可能なトラフィックスパイクを処理するために大きなストリーミングクラスタを維持しなければならない状況では、このクラスタを他の低優先度メッセージにも使うべきです（つまり、組織のための共通のFlink、Kafka、Sparkサービス）。

ユーザーからのポーリングまたはプルがプッシュより良いもう一つの状況は、ユーザーがファイアウォールで保護されている場合、または依存関係に頻繁な変更があり、プッシュリクエストが多すぎる場合です。プルはプッシュよりも1つ少ないセットアップステップで済みます。ユーザーは既に依存関係にリクエストを行っています。しかし、依存関係は通常ユーザーにリクエストを行いません。

逆（https://engineering.linkedin.com/blog/2019/data-hub）は、システムがクローラーを使って多くのソースからデータを収集する場合です。これらすべてのクローラーの開発と保守は複雑で面倒すぎるかもしれません。個々のデータプロバイダーが中央のリポジトリに情報をプッシュする方がスケーラブルかもしれません。プッシュはまた、よりタイムリーな更新を可能にします。

プッシュがプルより良いもう一つの例外は、オーディオやビデオのライブストリーミングなどの損失のあるアプリケーションです。これらのアプリケーションは最初に配信に失敗したデータを再送せず、一般にUDPを使って受信者にデータをプッシュします。

4.6.3 Kafka vs. RabbitMQ

実際にはほとんどの企業に共有のKafkaサービスがあり、他のサービスから使用されます。本書の残りでは、メッセージングまたはイベントストリーミングサービスが必要なときはKafkaを使います。面接では、意見の強い面接官の怒りを買うリスクを冒すよりも、KafkaとRabbitMQの詳細と違いについての知識を示し、そのトレードオフを議論する方が安全です。

どちらも不均一なトラフィックを平準化し、サービスがトラフィックスパイクで過負荷になることを防ぎ、高トラフィック期間を処理するためだけに大量のホストをプロビジョニングする必要がないためサービスをコスト効率良く保つために使えます。

KafkaはRabbitMQより複雑で、RabbitMQに対する機能のスーパーセットを提供します。言い換えれば、KafkaはRabbitMQの代わりに常に使えますが、逆はできません。

RabbitMQがシステムに十分な場合、RabbitMQの使用を提案するとともに、組織にはおそらく使えるKafkaサービスがあるので、RabbitMQのような別のコンポーネントのセットアップと保守（ロギング、モニタリング、アラートを含む）の手間を避けるためにそれを使えると述べてもよいでしょう。表4.1はKafkaとRabbitMQの違いを示しています。

アプリケーションをロードバランサーに接続し、ロードバランサーへの生産とそこからの消費を行うことで、アプリケーションレベルで自分でスケーラビリティを実装できる。しかしこれはKafkaよりもセットアップに多くの作業を要し、はるかに未成熟なため、多くの点でほぼ確実に劣る。

キューのイベントは消費後に削除されないため、同じイベントを繰り返し消費できる。これは障害耐性のためで、コンシューマがイベント処理を完了する前に失敗してイベントを再処理する必要がある場合に備える。

この点で、Kafkaで「キュー」という用語を使うのは概念的に不正確。実際にはリストである。しかし「Kafka queue」という用語は一般的に使われる。

Kafkaに保持期間を設定でき、デフォルトでは7日間で、イベントは消費されたかどうかに関係なく7日後に削除される。保持期間を無期限に設定してKafkaをデータベースとして使うこともできる。

「キュー」の定義通り、キューのメッセージはデキュー時に削除される（2021年7月26日にリリースされたRabbitMQ 3.9には、各メッセージの繰り返し消費を可能にするstream https://www.rabbitmq.com/streams.html 機能があるため、この違いは以前のバージョンにのみ存在する。）

複数のキューを作成して、メッセージごとに複数のコンシューマを許可することができる（コンシューマごとに1つのキュー）。しかしこれは複数のキューを持つ意図された使い方ではない。

優先度の概念がない。

AMQP標準のメッセージごとのキュー優先度の概念がある。優先度の異なる複数のキューを作成できる。キューのメッセージは、より高い優先度のキューが空になるまでデキューされない。公平性や飢餓の考慮はない。

4.6.4 ラムダアーキテクチャ

ラムダアーキテクチャは、バッチとストリーミングのパイプラインを並列に実行してビッグデータを処理するデータ処理アーキテクチャです。非公式には、同じ宛先を更新する並列の速いパイプラインと遅いパイプラインを持つことを指します。速いパイプラインは低レイテンシ（つまり高速な更新）のために一貫性と正確性をトレードオフし、遅いパイプラインはその逆です。速いパイプラインは次のような技法を採用します:

  • 近似アルゴリズム（17.7節で議論）。
  • Redisのようなメモリ内データベース。
  • 処理を高速化するため、速いパイプラインのノードは処理するデータをレプリケーションしないかもしれず、ノード停止からのデータ損失と低い正確性が生じる可能性があります。

遅いパイプラインは通常HiveやHDFSを伴うSparkなどのMapReduceデータベースを使います。ビッグデータを含み、一貫性と正確性が必要なシステムにはラムダアーキテクチャを提案できます。

様々なデータベースソリューションについての注

多くのデータベースソリューションがあります。一般的なものには様々なSQLディストリビューション、HadoopとHDFS、Kafka、Redis、Elasticsearchが含まれます。MongoDB、Neo4j、AWS DynamoDB、GoogleのFirebase Realtime Databaseなど、あまり一般的でないものもたくさんあります。一般に、あまり一般的でないデータベース、特にプロプライエタリデータベースの知識はシステムデザイン面接では期待されません。プロプライエタリデータベースが採用されることはまれです。スタートアップがプロプライエタリデータベースを採用する場合、できるだけ早くオープンソースデータベースへの移行を検討すべきです。データベースが大きいほどベンダーロックインが悪化し、移行プロセスがより困難で、エラーが発生しやすく、高価になります。

ラムダアーキテクチャの代替案はKappaアーキテクチャです。Kappaアーキテクチャは、単一の技術スタックでバッチおよびストリーミング処理の両方を実行する、ストリーミングデータを処理するためのソフトウェアアーキテクチャパターンです。Kafkaのような追記専用の不変ログを使って受信データを格納し、続いてストリーム処理を行い、ユーザーがクエリするためのデータベースに格納します。LambdaとKappaアーキテクチャの詳細な比較については17.9.1節を参照してください。

投稿管理とユーザー管理に分けて、いくつかのAPIエンドポイントを書き出してみましょう。（面接では、OpenAPI形式やGraphQLスキーマのような正式なAPI仕様を書き下す時間はないので、面接官には正式仕様を使ってAPIを定義できる旨を伝えつつ、時間の都合上、面接では大まかな書き出しを用いる、と説明できます。本書の以後ではこのことを繰り返しません。）

投稿のCRUD：

  • GET および DELETE /post/{id}
  • GET /post?search={search_string}。これは全投稿を取得するエンドポイントになり得ます。「search」クエリパラメータを持たせて投稿の内容を検索することもできます。また、ページネーション用のクエリパラメータも実装するかもしれません。これは12.7.1節で議論します。
  • POST および PUT /post
  • POST /contact
  • POST /report
  • DELETE /old_posts

ユーザー管理：

  • POST /signup。ユーザーアカウント管理について議論する必要はありません。
  • POST /login
  • DELETE /user

その他：

  • GET /health。通常はフレームワークによって自動生成されます。実装は単純に小さなGETリクエストを行い200が返ることを検証するだけでも構いませんし、各エンドポイントのP99や可用性などの統計値を含む詳細な実装にすることもできます。

商品カテゴリーによって異なる、さまざまなフィルタが存在します。簡略化のため、固定のフィルタ集合を仮定します。フィルタはフロントエンドとバックエンドの両方で実装できます。

  • 地区（Neighborhood）： enum
  • 最低 価格
  • 最高 価格
  • 商品状態： enum。値はNEW、EXCELLENT、GOOD、ACCEPTABLEを含みます。

GET /post エンドポイントには、投稿を検索するための「search」クエリパラメータを持たせることができます。

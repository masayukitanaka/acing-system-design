検索は多くのアプリケーションの一般的な機能です。ほとんどのフロントエンドアプリケーションは、ユーザーが目的のデータを素早く見つけられるように検索バーを提供します。データは Elasticsearch クラスタにインデックス化できます。

2.6.1 はじめに

検索バーは多くのアプリで一般的なUIコンポーネントです。単一の検索バーだけのこともあれば、フィルタリング用の他のフロントエンドコンポーネントを含むこともあります。図2.2は検索バーの例です。

図2.2 結果をフィルタリングするためのドロップダウンメニュー付きのGoogle検索バー。画像はGoogleから。

検索を実装する一般的な手法は次の通りです:

  1. SQLデータベース上でLIKE演算子とパターンマッチングを使った検索。クエリは SELECT <column> FROM <table> WHERE Lower(<column>) LIKE “%Lower(<search_term>)%” のようになるかもしれません。
  2. match-sorter（https://github.com/kentcdodds/match-sorter）のようなライブラリを使う。これは検索語を受け取りレコードに対してマッチングとソートを行うJavaScriptライブラリです。そのようなソリューションは各クライアントアプリケーションに個別に実装する必要があります。これは数GBまでのテキストデータ（つまり数百万レコードまで）に対して適切で技術的にシンプルなソリューションです。Webアプリケーションは通常、バックエンドからデータをダウンロードし、このデータは数メガバイトを超えないでしょう。さもなければアプリケーションは数百万ユーザーにスケールできません。モバイルアプリケーションはローカルにデータを格納できるので、理論的にはGB単位のデータを持つことが可能ですが、数百万の電話間でデータを同期するのは実用的ではないかもしれません。
  3. Elasticsearchのような検索エンジンを使う。このソリューションはスケーラブルでPB単位のデータを扱えます。

最初の手法には多くの制限があり、すぐに破棄されるか適切な検索エンジンに変更される一時的な実装としてのみ使用すべきです。欠点には次のものがあります:

  • 検索クエリのカスタマイズが困難。
  • ブースティング、重み付け、ファジー検索、ステミングやトークン化などのテキスト前処理のような高度な機能がない。

この議論は個々のレコードが小さい、つまり動画レコードではなくテキストレコードであることを想定しています。動画レコードの場合、インデックスと検索の操作は動画データに対して直接行うのではなく、付随するテキストメタデータに対して行います。検索エンジンでのインデックスと検索の実装は本書の範囲外です。

パート2の質問の議論ではこれらの手法を参照し、Elasticsearchの使用にはるかに多くの注意を払います。

2.6.2 Elasticsearchによる検索バーの実装

組織は、自社の多くのサービスの検索要件を提供するために共有のElasticsearchクラスタを持つことができます。本節では、まず基本的なElasticsearchの全文検索クエリを説明し、続いて既存のElasticsearchクラスタが与えられている場合に、サービスにElasticsearchを追加する基本的なステップを説明します。本書ではElasticsearchクラスタのセットアップは議論せず、Elasticsearchの概念や用語を詳細に説明することもしません。例には第1章のBeigelアプリを使います。

ファジーマッチング付きの基本的な全文検索を提供するため、Elasticsearchサービスにクエリを転送するGETエンドポイントに検索バーを接続できます。Elasticsearchクエリは Elasticsearch インデックス（リレーショナルデータベースのデータベースに相当）に対して実行されます。GETクエリが検索結果のリストを伴う2xxレスポンスを返した場合、フロントエンドはリストを表示する結果ページを読み込みます。

例えば、Beigelアプリが検索バーを提供しており、ユーザーが「sesame」という用語を検索した場合、Elasticsearchリクエストは次のようになるかもしれません。

検索語はクエリパラメータに含めることができ、これは完全一致のみを許可します:

GET /beigel-index/_search?q=sesame

JSONリクエストボディも使用でき、これにより本書の範囲外であるElasticsearchの完全なDSLを使用できます:

GET /beigel-index/_search

{

  "query": {z6

    "match": {

      "query": "sesame",

      "fuzziness": "AUTO"

    }  

  }

}

"fuzziness": "AUTO" はファジー（近似）マッチングを有効にするためのもので、検索語や検索結果にスペルミスが含まれる場合など、多くのユースケースがあります。

結果は次の例のように、関連性の降順でソートされたヒットのJSON配列として返されます。バックエンドはフロントエンドに結果を渡し、フロントエンドがそれをパースしてユーザーに提示できます。

2.6.3 Elasticsearchインデックスと取り込み

Elasticsearchインデックスの作成は、ユーザーが検索バーから検索クエリを送信したときに検索されるべきドキュメントを取り込み、その後インデックス化操作を行うことで構成されます。

Bulk APIを使った定期的またはイベントトリガーのインデックスまたは削除リクエストでインデックスを最新の状態に保つことができます。

インデックスのマッピングを変更する方法の一つは、新しいインデックスを作成し古いものを破棄することです。もう一つの方法はElasticsearchの再インデックス操作を使うことですが、内部のLucene commit操作が各書き込みリクエストの後に同期的に発生するためコストがかかります（https://www.elastic.co/guide/en/elasticsearch/reference/current/index-modules-translog.html#index-modules-translog）。

Elasticsearchインデックスを作成するには、検索したいすべてのデータをElasticsearchのドキュメントストアに格納する必要があり、全体的なストレージ要件が増加します。インデックスに送信するデータのサブセットだけを送るような様々な最適化があります。

2.6.4 SQLの代わりにElasticsearchを使う

ElasticsearchはSQLのように使うことができます。Elasticsearchにはquery context vs. filter contextの概念があります（https://www.elastic.co/guide/en/elasticsearch/reference/current/query-filter-context.html）。ドキュメントによれば、filter contextでは、クエリ句は「このドキュメントはこのクエリ句にマッチするか?」という質問に答えます。回答は単純なyesかnoで、スコアは計算されません。query contextでは、クエリ句は「このドキュメントはこのクエリ句にどれだけよくマッチするか?」という質問に答えます。クエリ句は、ドキュメントがマッチするかどうかを判定し、関連スコアを計算します。本質的に、query contextはSQLクエリに、filter contextは検索に類似しています。

SQLの代わりにElasticsearchを使えば、検索とクエリの両方が可能になり、重複したストレージ要件が排除され、SQLデータベースの保守オーバーヘッドが排除されます。データ格納にElasticsearchだけを使うサービスを見たことがあります。

しかし、Elasticsearchはリレーショナルデータベースを置き換えるよりも、それらを補完するためにしばしば使われます。スキーマレスデータベースであり、主キーや外部キーといったテーブル間の関係や正規化の概念がありません。SQLとは異なり、Elasticsearchは Command Query Responsibility Segregation（1.4.6節参照）やACIDも提供しません。

さらに、Elasticsearch Query Language（EQL）はJSONベースの言語で、冗長で学習曲線があります。SQLはデータアナリストや非技術者を含む非開発者にとって馴染みがあります。非技術者ユーザーは1日で基本的なSQLを簡単に学べます。

Elasticsearch SQLは2018年6月のElasticsearch 6.3.0のリリースで導入されました（https://www.elastic.co/blog/an-introduction-to-elasticsearch-sql-with-practical-examples-part-1 および https://www.elastic.co/what-is/elasticsearch-sql）。すべての一般的なフィルタリングと集約操作をサポートします（https://www.elastic.co/guide/en/elasticsearch/reference/current/sql-functions.html）。これは有望な発展です。SQLの優位性は確立されていますが、今後数年間、より多くのサービスがすべてのデータ格納と検索にElasticsearchを使用する可能性があります。

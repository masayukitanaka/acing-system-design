本書は、アプリの典型的な初期セットアップと、必要に応じてアプリのサービスにスケーラビリティを追加する一般的なアプローチについて簡単に説明することから始めます。その過程で、多くの用語や概念、そしてテック企業に必要な多種多様なサービスを紹介し、それらは本書の残りの部分でより詳細に議論します。

定義 サービスのスケーラビリティとは、負荷の変化に対応するために、そのサービスに割り当てるリソースを容易かつコスト効率よく変動させる能力を指します。これはユーザー数やシステムへのリクエストの増加・減少の両方に当てはまります。これは第3章で詳しく議論します。

1.4.1 始まり: アプリの小規模な初期デプロイ

職人の作るベーグルへの関心が高まる波に乗って、近所のベーグルカフェについて投稿を読んだり作成したりできる、Beigelという素晴らしいコンシューマー向けアプリを構築しました。

最初のBeigelは主に以下のコンポーネントで構成されています:

  • コンシューマーアプリ群。本質的には同じアプリで、よくある3つのプラットフォームそれぞれに1つずつ存在します:
  • ブラウザアプリ。これはJavaScriptランタイムサービスにリクエストを送るReactJS製のブラウザコンシューマーアプリです。ユーザーがダウンロードする必要のあるJavaScriptバンドルのサイズを減らすために、Brotliで圧縮しています。Gzipはより古く一般的な選択肢ですが、Brotliの方がより小さな圧縮ファイルを生成します。
  • iOSアプリ。コンシューマーのiOSデバイスにダウンロードされます。
  • Androidアプリ。同じくコンシューマーのAndroidデバイスにダウンロードされます。
  • コンシューマーアプリにサービスを提供するステートレスなバックエンドサービス。GoまたはJavaのサービスでよいでしょう。
  • 1台のクラウドホスト内に含まれるSQLデータベース。

主なサービスは2つあります: フロントエンドサービスとバックエンドサービスです。図1.1にこれらのコンポーネントを示します。図にあるように、コンシューマーアプリはクライアントサイドのコンポーネントであり、サービスとデータベースはサーバーサイドのコンポーネントです。

注 ブラウザとバックエンドサービスの間にフロントエンドサービスが必要な理由については、6.5.1節および6.5.2節を参照してください。

図1.1 アプリの初期システム設計。3つのクライアントアプリケーションと2つのサーバーアプリケーション（SQLアプリケーション/データベースを除く）を持つ根拠についてのより詳細な議論は、第6章を参照してください。

サービスを初めてローンチするとき、ユーザー数はわずかで、リクエストレートも低いかもしれません。低いリクエストレートを処理するには1台のホストで十分なこともあります。すべてのリクエストをこのホストに向けるようDNSを設定します。

最初は、両方のサービスを同じデータセンター内、それぞれ1台のクラウドホスト上でホストできます。（クラウドとベアメタルの比較は次の節で行います。）ブラウザアプリからのリクエストすべてをNode.jsホストへ、Node.jsホストと2つのモバイルアプリからのリクエストをバックエンドホストへ向けるよう、DNSを設定します。

1.4.2 GeoDNSによるスケーリング

数ヶ月後、Beigelはアジア、ヨーロッパ、北アメリカで数十万のデイリーアクティブユーザーを獲得しました。ピークトラフィックの時間帯には、バックエンドサービスは毎秒数千のリクエストを受け取り、監視システムはタイムアウトによるステータスコード504のレスポンスを報告し始めています。システムをスケールアップしなければなりません。

トラフィックの増加を観察しており、この状況に備えていました。標準的なベストプラクティスに従いサービスはステートレスなので、複数の同一のバックエンドホストをプロビジョニングし、それぞれを世界各地の異なるデータセンターに配置できます。図1.2を参照すると、クライアントが beigel.com というドメインを通じてバックエンドにリクエストを行うとき、GeoDNSを使ってクライアントを最も近いデータセンターに向けます。

図1.2 サービスを地理的に分散した複数のデータセンターにプロビジョニングできます。クライアントの位置（IPアドレスから推測される）に応じて、クライアントは最も近いデータセンターのホストのIPアドレスを取得し、そこにリクエストを送信します。クライアントはこのホストIPアドレスをキャッシュできます。

サービスが特定の国または地理的地域のユーザーを主に対象とする場合、レイテンシを最小化するために通常は近隣のデータセンターでサービスをホストします。サービスが地理的に広く分散したユーザーベースを対象とする場合、複数のデータセンターでホストし、最も近いデータセンターでホストされているサービスのIPアドレスをGeoDNSでユーザーに返すことができます。これは、ドメインに複数の場所のための複数のAレコードと、その他の場所のためのデフォルトIPアドレスを割り当てることで行われます。（Aレコードは、ドメインをIPアドレスにマッピングするDNS設定です。）

クライアントがサーバーにリクエストを行うと、GeoDNSはクライアントのIPアドレスからクライアントの位置を取得し、対応するホストのIPアドレスをクライアントに割り当てます。可能性は低いものの、データセンターにアクセスできない場合に備え、GeoDNSは別のデータセンター上のサービスのIPアドレスを返すこともできます。このIPアドレスは、ユーザーのインターネットサービスプロバイダ（ISP）、OS、ブラウザなど、様々なレベルでキャッシュされる可能性があります。

1.4.3 キャッシュサービスの追加

図1.3を参照すると、次にRedisキャッシュサービスをセットアップして、コンシューマーアプリからのキャッシュされたリクエストを処理します。トラフィックが多い特定のバックエンドエンドポイントを選んでキャッシュから提供します。これによりユーザーベースとリクエスト負荷の増加が続く中でも、ある程度の時間的猶予を得ました。今、さらにスケールアップするための追加のステップが必要です。

図1.3 サービスへのキャッシュ追加。トラフィックが多い特定のバックエンドエンドポイントはキャッシュ可能です。バックエンドは、キャッシュミス時、またはキャッシュされていないSQLデータベース/テーブルに対しては、データベースにデータをリクエストします。

1.4.4 コンテンツデリバリーネットワーク

ブラウザアプリは、どのユーザーにも同じように表示され、ユーザー入力の影響を受けない静的コンテンツ/ファイル（JavaScript、CSSライブラリ、一部の画像や動画など）をホストしていました。これらのファイルをアプリのソースコードリポジトリ内に置いており、ユーザーはアプリの残りの部分と一緒にNode.jsサービスからダウンロードしていました。図1.4を参照して、静的コンテンツをホストするためにサードパーティのコンテンツデリバリーネットワーク（CDN）を使用することにしました。ファイルをホストするのに十分な容量のCDNを選択してプロビジョニングし、ファイルをCDNインスタンスにアップロードし、CDNのURLからファイルを取得するようにコードを書き換え、ソースコードリポジトリからファイルを削除しました。

図1.4 サービスへのCDN追加。クライアントはバックエンドからCDNアドレスを取得することも、特定のCDNアドレスをクライアントやNode.jsサービスにハードコードすることもできます。

図1.5を参照すると、CDNは静的ファイルのコピーを世界中の様々なデータセンターに保存するので、ユーザーは最も低いレイテンシで提供できるデータセンター、通常は地理的に最も近いデータセンターからこれらのファイルをダウンロードできます。ただし、最も近いデータセンターが大量のトラフィックを処理していたり部分的な障害を起こしていたりすると、他のデータセンターの方が高速な場合もあります。

図1.5 左の図は、すべてのクライアントが同じホストからダウンロードする様子を示しています。右の図は、クライアントがCDNの様々なホストからダウンロードする様子を示しています。（著作権 cc-by-sa https://creativecommons.org/licenses/by-sa/3.0/. 画像: Kanoha提供 https://upload.wikimedia.org/wikipedia/commons/f/f9/NCDN_-_CDN.png.)

CDNを使用することで、レイテンシ、スループット、信頼性、コストが改善されました。（これらの概念はすべて第3章で議論します。）CDNを使うと、メンテナンス、統合のオーバーヘッド、カスタマーサポートがより大きな負荷に分散されるため、需要が増えるにつれて単位コストが低下します。

人気のCDNには CloudFlare、Rackspace、AWS CloudFront などがあります。

1.4.5 水平スケーラビリティとクラスタ管理、継続的インテグレーション、継続的デプロイメントについての簡単な議論

フロントエンドとバックエンドのサービスは冪等（idempotent）であり（冪等性の利点については4.6.1、6.1.2、7.7節で議論します）、したがって水平にスケーラブルなので、ソースコードを書き換えることなく、より大きなリクエスト負荷を支えるためにより多くのホストをプロビジョニングし、必要に応じてフロントエンドまたはバックエンドサービスをそれらのホストにデプロイできます。

各サービスには、ソースコードに取り組む複数のエンジニアがいます。エンジニアは毎日新しいコミットを提出します。このより大きなチームとより速い開発をサポートするため、ソフトウェア開発・リリースのプラクティスを変更し、大規模クラスタを管理するためのインフラを開発する2人のDevOpsエンジニアをその過程で採用します。サービスのスケーリング要件はすぐに変わる可能性があるので、クラスタのサイズを簡単に変更できるようにしたいと考えます。新しいホストにサービスと必要な設定を簡単にデプロイできる必要があります。また、サービスのクラスタ内のすべてのホストにコード変更を簡単にビルドしてデプロイしたいとも考えます。大規模なユーザーベースを実験に活用し、さまざまなホストに異なるコードや設定をデプロイすることもできます。本節では、水平スケーラビリティと実験のためのクラスタ管理について簡単に議論します。

CI/CD と Infrastructure as Code

バグをリリースするリスクを最小限に抑えながら新機能を素早くリリースできるようにするため、Jenkinsを用いた継続的インテグレーションと継続的デプロイメント、そしてユニットテストや統合テストのツールを採用します。（CI/CDの詳細な議論は本書の範囲外です。）サービスのコンテナ化にはDockerを、スケーリングやロードバランシングを含むホストクラスタの管理にはKubernetes（またはDocker Swarm）を、様々なクラスタ上で動作する各種サービスの構成管理にはAnsibleまたはTerraformを使用します。

注 Mesosは広く時代遅れと見なされています。Kubernetesが明確な勝者です。関連する記事として https://thenewstack.io/apache-mesos-narrowly-avoids-a-move-to-the-attic-for-now/ と https://www.datacenterknowledge.com/business/after-kubernetes-victory-its-former-rivals-change-tackがあります。

Terraformを使えば、インフラエンジニアは複数のクラウドプロバイダーと互換性のある単一の設定を作成できます。設定はTerraformのドメイン固有言語（DSL）で記述され、クラウドAPIと通信してインフラをプロビジョニングします。実際には、Terraform設定にベンダー固有のコードが含まれることがありますが、これは最小限に抑えるべきです。全体的な結果として、ベンダーロックインが少なくなります。

このアプローチは Infrastructure as Codeとも呼ばれます。Infrastructure as Codeとは、物理的なハードウェア構成や対話型の構成ツールではなく、機械可読の定義ファイルを通じてコンピュータのデータセンターを管理・プロビジョニングするプロセスのことです（Wittig, Andreas; Wittig, Michael [2016]. Amazon Web Services in Action. Manning Publications. p. 93. ISBN 978-1-61729-288-0）。

段階的なロールアウトとロールバック

本節では、段階的なロールアウトとロールバックについて簡単に議論し、次節での実験との対比をしやすくします。

本番環境にビルドをデプロイするときは、段階的に行うことがあります。ビルドを特定の割合のホストにデプロイし、それを監視してから割合を増やし、本番ホストの100%がこのビルドを実行するまでこのプロセスを繰り返します。例えば、1%、5%、10%、25%、50%、75%、最後に100%へとデプロイすることがあります。次のような問題を検出した場合、手動または自動でデプロイをロールバックすることがあります:

  • テストをすり抜けたバグ。
  • クラッシュ。
  • レイテンシやタイムアウトの増加。
  • メモリリーク。
  • CPU、メモリ、ストレージ使用率などのリソース消費の増加。
  • ユーザー離脱（チャーン）の増加。段階的なロールアウトでは、新規ユーザーがサインオンしてアプリを使い始め、特定のユーザーがアプリの使用をやめる可能性があることを考慮する必要があります。新しいビルドに段階的に増加する割合のユーザーをさらすことで、ユーザー離脱への影響を調べられます。ユーザー離脱は、上記の要因や、多くのユーザーが変更を気に入らないといった予期しない問題により発生する可能性があります。

例えば、新しいビルドが許容できないレベルまでレイテンシを増加させる可能性があります。これを処理するためにキャッシュと動的ルーティングの組み合わせを使えます。サービスは1秒のレイテンシを指定するかもしれません。クライアントが新しいビルドにルーティングされるリクエストを行い、タイムアウトが発生した場合、クライアントはキャッシュから読み取るか、リクエストを繰り返して古いビルドを持つホストにルーティングされることがあります。タイムアウトのトラブルシューティングができるように、リクエストとレスポンスをログに記録するべきです。

CDパイプラインを設定して本番クラスタを複数のグループに分け、CDツールが各グループの適切なホスト数を決定し、ホストをグループに割り当てるようにできます。クラスタのサイズを変更した場合、再割り当てや再デプロイが行われる可能性があります。

実験（Experimentation）

アプリケーションで新機能を開発する（または機能を削除する）際のUX変更や美的デザインを行う際、すべてのユーザーに一度に展開するのではなく、段階的に増加する割合のユーザーに展開したい場合があります。実験の目的は、UX変更がユーザー行動に与える影響を判断することです。これは、新しいデプロイメントがアプリケーションのパフォーマンスやユーザー離脱に与える影響を見る段階的ロールアウトとは対照的です。一般的な実験アプローチには、A/Bテストや多変量テスト（multi-armed banditなど）があります。これらのトピックは本書の範囲外です。A/Bテストの詳細については https://www.optimizely.com/optimization-glossary/ab-testing/を、多変量テストについては Experimentation for Engineers（David Sweet著、Manning Publications, 2023）または https://www.optimizely.com/optimization-glossary/multi-armed-bandit/ でmulti-armed banditの入門を参照してください。)

実験は、パーソナライズされたユーザー体験を提供するためにも行われます。

実験と段階的ロールアウト・ロールバックのもう一つの違いは、実験では様々なビルドを実行するホストの割合がしばしば、その目的のために設計された実験ツールやフィーチャートグルツールによって調整される一方、段階的ロールアウト・ロールバックでは、問題が検出された場合に手動または自動でホストを以前のビルドに戻すためにCDツールが使われる点です。

CDと実験により、新しいデプロイメントや機能への短いフィードバックサイクルが可能になります。

Webやバックエンドアプリケーションでは、通常、各ユーザー体験（UX）は異なるビルドにパッケージ化されます。特定の割合のホストが異なるビルドを含むことになります。モバイルアプリは通常異なります。多くのユーザー体験が同じビルドにコーディングされますが、各個別ユーザーはそれらのユーザー体験の一部にのみさらされます。これには主に次のような理由があります:

  • モバイルアプリケーションのデプロイメントは、アプリストアを通じて行わなければなりません。ユーザーのデバイスに新しいバージョンをデプロイするのに何時間もかかることがあります。デプロイメントを素早くロールバックする方法はありません。
  • Wi-Fiと比較して、モバイルデータは遅く、信頼性が低く、より高価です。低速で信頼性が低いということは、多くのコンテンツをオフラインで、つまり既にアプリ内で提供する必要があるということです。多くの国でモバイルデータプランは依然として高価で、データ上限や超過料金が伴うことがあります。これらの料金にユーザーをさらすことは避けるべきで、さもないとアプリの使用が減ったり、まるごとアンインストールされたりするかもしれません。コンポーネントやメディアをダウンロードするデータ使用量を最小化しながら実験を行うため、これらのコンポーネントやメディアをすべてアプリに含めて、目的のサブセットを個々のユーザーにだけ見せるという単純な方法を採ります。
  • モバイルアプリには、自分には当てはまらず一部のユーザーが決して使わない多くの機能が含まれることもあります。例えば、15.1節ではアプリ内の様々な支払い方法を議論しています。世界には数千の支払いソリューションがあるかもしれません。アプリは、各ユーザーに彼らが利用できる支払いソリューションの小さなサブセットを提示できるよう、すべての支払いソリューションのコードとSDKを含む必要があります。

これらすべての結果として、モバイルアプリのサイズが100MBを超えることもあります。これに対処する技術は本書の範囲外です。バランスを取り、トレードオフを考慮する必要があります。例えば、YouTubeのモバイルアプリのインストールが多くのYouTube動画を含むことができないのは明らかです。

1.4.6 機能的パーティショニングと横断的関心事の集約

機能的パーティショニングとは、様々な機能を異なるサービスやホストに分離することです。多くのサービスには、共有サービスに抽出できる共通の関心事があります。第6章でその動機、利点、トレードオフを議論します。

共有サービス

私たちの会社は急速に拡大しています。デイリーアクティブユーザー数は数百万に達しました。エンジニアリングチームをiOSエンジニア5名、Androidエンジニア5名、フロントエンドエンジニア10名、バックエンドエンジニア100名に拡大し、データサイエンスチームを作ります。

拡大したエンジニアリングチームは、コンシューマーが直接使うアプリ以外の多くのサービス、例えば拡大するカスタマーサポート部門やオペレーション部門のためのサービスにも取り組めます。コンシューマーアプリ内に、コンシューマーがカスタマーサポートに連絡したり、オペレーションが製品のバリエーションを作成・ローンチしたりするための機能を追加します。

多くのアプリには検索バーが含まれます。Elasticsearchを使った共有検索サービスを作成します。

水平スケーリングに加えて、機能的パーティショニングを使い、機能と地理に基づいてパーティショニングすることで、データ処理とリクエストを地理的に分散した多数のホストに分散させます。すでにキャッシュ、Node.jsサービス、バックエンドサービス、データベースサービスを別々のホストに機能的パーティショニングしましたが、他のサービスについても機能的パーティショニングを行い、各サービスを地理的に分散した独自のホストクラスタに配置します。図1.6はBeigelに追加する共有サービスを示しています。

図1.6 機能的パーティショニング。共有サービスの追加。

ログベースのメッセージブローカーで構成されるロギングサービスを追加しました。Elastic Stack（Elasticsearch、Logstash、Kibana、Beats）を使えます。また、ZipkinやJaegerなどの分散トレーシングシステム、または分散ロギングを使い、リクエストが多数のサービスを通過する様子をトレースします。サービスは各リクエストにスパンIDを付与するので、トレースとして組み立てて分析できます。2.5節でロギング、モニタリング、アラートについて議論します。

モニタリングおよびアラートサービスも追加しました。顧客サポート従業員が顧客をよりよく支援するための社内ブラウザアプリを構築します。これらのアプリは顧客が生成したコンシューマーアプリのログを処理し、優れたUIで提示することで、カスタマーサポート従業員が顧客の問題をより簡単に理解できるようにします。

APIゲートウェイとサービスメッシュは、横断的関心事を集約する2つの方法です。他の方法にはデコレータパターンやアスペクト指向プログラミングがありますが、これらは本書の範囲外です。

APIゲートウェイ

この時点で、アプリユーザーは私たちのAPIリクエストの半数未満を占めるようになっています。ほとんどのリクエストは他社からのもので、それらの会社はアプリ内活動に基づいてユーザーに有用な製品やサービスをレコメンドするなどのサービスを提供しています。一部のAPIを外部開発者に公開するため、APIゲートウェイ層を開発します。

APIゲートウェイは、クライアントリクエストを適切なバックエンドサービスにルーティングするリバースプロキシです。多くのサービスに共通する機能を提供することで、個々のサービスがそれらを重複して実装しないようにします:

  • 認可と認証、その他のアクセス制御とセキュリティポリシー
  • リクエストレベルでのロギング、モニタリング、アラート
  • レートリミット
  • 課金
  • アナリティクス

APIゲートウェイとそのサービスを含む初期アーキテクチャを図1.7に示します。サービスへのリクエストは集中型のAPIゲートウェイを通ります。APIゲートウェイは前述のすべての機能を実行し、DNSルックアップを行い、その後関連するサービスのホストにリクエストを転送します。APIゲートウェイは、DNS、ID・アクセス制御管理、レートリミット設定サービスなどのサービスにもリクエストを行います。また、APIゲートウェイを通じて行われたすべての設定変更をログに記録します。

図1.7 APIゲートウェイとサービスを含む初期アーキテクチャ。サービスへのリクエストはAPIゲートウェイを通ります。

しかし、このアーキテクチャには次のような欠点があります。APIゲートウェイはレイテンシを追加し、大規模なホストクラスタを必要とします。APIゲートウェイのホストと、特定のリクエストを処理するサービスのホストが異なるデータセンターにある場合があります。APIゲートウェイホストとサービスホストを介してリクエストをルーティングしようとするシステム設計は、ぎこちなく複雑な設計になります。

解決策は、サービスメッシュ（サイドカーパターンとも呼ばれる）の使用です。サービスメッシュは第6章でさらに議論します。図1.8は私たちのサービスメッシュを示しています。Istioのようなサービスメッシュフレームワークを使えます。各サービスの各ホストは、メインのサービスと並んでサイドカーを実行できます。これを実現するためにKubernetesポッドを使います。各ポッドには、そのサービス（1つのコンテナ内）とそのサイドカー（別のコンテナ内）を含めることができます。ポリシーを設定するための管理インターフェースを提供し、これらの設定をすべてのサイドカーに配布できます。

図1.8 サービスメッシュの図解。Prometheusは各プロキシホストにリクエストを行いメトリクスをプル/スクレイプしますが、矢印が多すぎて図が乱雑で分かりにくくなるため、図には示していません。図は https://livebook.manning.com/book/cloud-native/chapter-10/146から引用・改変。

このアーキテクチャでは、すべてのサービスリクエストとレスポンスはサイドカーを経由してルーティングされます。サービスとサイドカーは同じホスト（つまり同じマシン）にあるので、localhost経由で互いにアドレス指定でき、ネットワークレイテンシはありません。ただし、サイドカーはシステムリソースを消費します。

サイドカーレスサービスメッシュ — 最先端

サービスメッシュは、システムのコンテナ数をほぼ倍増させる必要がありました。内部サービス間の通信（イングレスまたは東西通信）を伴うシステムでは、サイドカープロキシのロジックを、サービスホストにリクエストを行うクライアントホストに配置することで、この複雑さを減らせます。サイドカーレスサービスメッシュの設計では、クライアントホストがコントロールプレーンから設定を受け取ります。クライアントホストはコントロールプレーンAPIをサポートする必要があり、そのため適切なネットワーク通信ライブラリも含める必要があります。

サイドカーレスサービスメッシュの制限は、サービスと同じ言語のクライアントが必要となる点です。

サイドカーレスサービスメッシュプラットフォームの開発は初期段階にあります。Google Cloud Platform (GCP) Traffic Director は、2019年4月にリリースされた実装です（https://cloud.google.com/blog/products/networking/traffic-director-global-traffic-management-for-open-service-mesh）。

Command Query Responsibility Segregation (CQRS)

Command Query Responsibility Segregation (CQRS) は、コマンド/書き込み操作とクエリ/読み取り操作を機能的に別々のサービスにパーティショニングするマイクロサービスパターンです。メッセージブローカーやETLジョブはCQRSの例です。あるテーブルにデータを書き込み、それを変換して別のテーブルに挿入するような設計はすべてCQRSの例です。CQRSは複雑さを伴いますが、レイテンシが低く、スケーラビリティが優れ、保守と利用が容易です。書き込みサービスと読み取りサービスは別々にスケールできます。

本書では明示的に名指しはしないものの、CQRSの例を多く目にすることになります。第15章にはそのような例の1つがあり、Airbnbのホストが Listing Service に書き込み、ゲストは Booking Service から読み取ります。（ただし、Booking Service はゲストが予約をリクエストするための書き込みエンドポイントも提供します。これはホストがリスティングを更新することとは無関係です。）

CQRSのより詳細な定義は他のソースで簡単に見つけられます。

1.4.7 バッチおよびストリーミングのExtract, Transform, Load (ETL)

一部のシステムは予測不可能なトラフィックスパイクを抱えており、特定のデータ処理リクエストは同期的（つまり即座に処理してレスポンスを返す）である必要はありません:

  • データベースへの大規模クエリを伴う一部のリクエスト（ギガバイト規模のデータを処理するクエリなど）。
  • リクエストが行われたときにだけ処理するのではなく、リクエストに先立って特定のデータを定期的に前処理する方が理にかなっている場合があります。例えば、アプリのホームページで、過去1時間または7日間にすべてのユーザーで最も頻繁に学習された上位10単語を表示するとします。この情報は1時間ごとまたは1日ごとに事前処理しておくべきです。さらに、この処理結果はすべてのユーザーで再利用でき、ユーザーごとに処理を繰り返す必要はありません。
  • もう一つの例として、ユーザーに数時間や数日古いデータを見せても許容される場合があります。例えば、ユーザーは自分の共有コンテンツを閲覧したユーザー数の最新統計を見る必要はありません。数時間古い統計を見せても許容されます。
  • 即座に実行する必要のない書き込み（例: INSERT、UPDATE、DELETEのデータベースリクエスト）。例えば、ロギングサービスへの書き込みは、ロギングサービスホストのハードディスクドライブに即座に書き込まれる必要はありません。これらの書き込みリクエストはキューに置かれ、後で実行できます。

ロギングのような、多くの他のシステムから大量のリクエストを受け取る特定のシステムの場合、ETLのような非同期アプローチを使用しなければ、ロギングシステムクラスタは、これらすべてのリクエストを同期的に処理するために何千ものホストを持たなければならなくなります。

そのようなバッチジョブには、Kafka（AWSを使う場合はKinesis）のようなイベントストリーミングシステムと、Airflowのようなバッチ ETLツールを組み合わせて使えます。

定期的にバッチジョブを実行するのではなく、データを継続的に処理したい場合は、Flinkのようなストリーミングツールを使用できます。例えば、ユーザーがアプリにデータを入力し、それを使って数秒または数分以内に特定のレコメンドや通知を送りたい場合、最近のユーザー入力を処理するFlinkパイプラインを作成できます。ロギングシステムは通常、絶え間ないリクエストのストリームを期待するためストリーミングです。リクエストの頻度が少ない場合は、バッチパイプラインで十分です。

1.4.8 その他の一般的なサービス

私たちの会社が成長し、ユーザーベースが拡大するにつれて、より多くの製品を開発します。製品はこの大規模で成長中の多様なユーザーベースに応えるため、ますますカスタマイズ可能でパーソナライズされたものになるべきです。この成長に伴う新しい要件を満たし、それを活用するためには、他の多くのサービスが必要になります。それらには次のようなものが含まれます:

  • 外部ユーザーの認証および認可のための、顧客/外部ユーザーの資格情報管理。
  • データベースサービスを含む様々なストレージサービス。各システムの特定の要件により、使用するデータを永続化、処理、提供するための最適な方法は異なります。さまざまなテクノロジーや手法を使う様々な共有ストレージサービスを開発・保守する必要があります。
  • 非同期処理。大規模なユーザーベースは、より多くのホストを必要とし、サービスへの予測不可能なトラフィックスパイクを生じさせる可能性があります。トラフィックスパイクを処理するには、ハードウェアを効率的に活用し、不要なハードウェア支出を減らすために非同期処理が必要です。
  • 分析や機械学習のためのノートブックサービス（実験、モデル作成、デプロイメントを含む）。大規模な顧客ベースを実験に活用して、ユーザーの好みを発見し、ユーザー体験をパーソナライズし、より多くのユーザーを惹きつけ、収益を増やす他の方法を発見できます。
  • 社内検索とそのサブ問題（例: オートコンプリート/タイプアヘッドサービス）。多くのウェブまたはモバイルアプリケーションには、ユーザーが目的のデータを検索するための検索バーを設けられます。
  • プライバシーコンプライアンスのサービスおよびチーム。ユーザー数の拡大と大量の顧客データは、データを盗もうとする外部・内部の悪意ある行為者を引き寄せます。大規模なユーザーベースに対するプライバシー侵害は多くの人々や組織に影響を与えます。ユーザーのプライバシーを保護するために投資する必要があります。
  • 不正検出。会社の収益が増加すると犯罪者や詐欺師にとって魅力的な標的となるため、効果的な不正検出システムは必須です。

1.4.9 クラウド vs. ベアメタル

自社でホストとデータセンターを管理することも、クラウドベンダーにアウトソースすることもできます。本節では両アプローチの比較分析を行います。

一般的な考慮事項

本節の冒頭で、ベアメタル（自社で物理マシンを所有・管理すること）ではなく、クラウドサービス（AmazonのAWS、DigitalOcean、Microsoft Azureなどのプロバイダーからホストを借りること）を使用することにしました。

クラウドプロバイダーは、CI/CD、ロギング、モニタリング、アラート、キャッシュ・SQL・NoSQLなど様々なデータベースタイプの簡略化されたセットアップと管理など、必要となる多くのサービスを提供します。

最初からベアメタルを選んでいた場合、必要なこれらのサービスをすべて自分でセットアップして保守する必要があったでしょう。これは機能開発から注意と時間を奪い、会社にとって高くつく可能性があります。

エンジニアリング工数のコストとクラウドツールのコストも比較する必要があります。エンジニアは非常に高価なリソースであり、金銭的に高くつくだけでなく、優秀なエンジニアはやりがいのある仕事を好む傾向があります。一般的なサービスの小規模なセットアップなどの雑務で退屈させると、他の会社に移ってしまい、競争の激しい採用市場では代わりを見つけるのが難しくなることがあります。

クラウドツールは、ベアメタルインフラをセットアップ・保守するエンジニアを雇うよりも安いことが多いです。私たちは、専業のクラウドプロバイダーが持つ規模の経済とそれに伴う単位コスト効率、または専門的な専門知識を持っていない可能性が高いです。会社が成功すれば、ベアメタルを検討できるだけの規模の経済を持つ成長段階に達するかもしれません。

ベアメタルの代わりにクラウドサービスを使うことには、次のような他の利点もあります。

セットアップの容易さ

クラウドプロバイダーのブラウザアプリ上では、目的に最も適したパッケージを簡単に選択できます。ベアメタルでは、Apacheのようなサーバーソフトウェアのインストールや、ネットワーク接続・ポートフォワーディングのセットアップなどのステップが必要になります。

コスト上の利点

クラウドには物理マシン/サーバーを購入する初期費用がありません。クラウドベンダーでは、使用量に応じた支払いが可能で、まとめ割引が提供されることもあります。予測不可能に変化する要件に対してスケールアップ・ダウンするのが容易で素早くできます。ベアメタルを選ぶと、物理マシンが少なすぎたり多すぎたりする状況に陥ることがあります。また、一部のクラウドプロバイダーは「オートスケーリング」サービスを提供し、現在の負荷に合わせてクラスタを自動的にサイズ変更します。

とはいえ、クラウドが常にベアメタルより安いわけではありません。Dropbox（https://www.geekwire.com/2018/dropbox-saved-almost-75-million-two-years-building-tech-infrastructure/）やUber（https://www.datacenterknowledge.com/uber/want-build-data-centers-uber-follow-simple-recipe）は、要件上それがよりコスト効率の良い選択であったため、自社のデータセンターでホストしている企業の例です。

クラウドサービスは優れたサポートと品質を提供することがある

逸話的な証拠は、クラウドサービスは一般的に優れたパフォーマンス、ユーザー体験、サポートを提供し、障害が少なく深刻度も低いことを示唆しています。考えられる理由の一つは、顧客を惹きつけ維持するために市場で競争力がなければならないクラウドサービスに対し、ベアメタルは組織のユーザーが使うしかないという違いです。多くの組織は、内部ユーザーや従業員よりも顧客により価値を置き、注意を払う傾向があります。これはおそらく、顧客からの収益は直接的に測定できる一方、内部ユーザーへの高品質なサービスとサポートの提供による恩恵は定量化しにくいためです。同様の論理で、低品質な内部サービスによる収益や士気の損失も定量化しにくいです。クラウドサービスには、ベアメタルにはない規模の経済もあるかもしれません。クラウドサービスのチームの努力がより大きなユーザーベースに分散されるからです。

外部向けのドキュメントは、内部向けのドキュメントよりも良いことがあります。より良く書かれ、より頻繁に更新され、検索しやすい整理されたウェブサイトに置かれているかもしれません。割り当てられるリソースも多く、動画やステップバイステップのチュートリアルが提供されることもあります。

外部サービスは、内部サービスより高品質な入力バリデーションを提供することがあります。簡単な例を考えてみましょう。あるUIフィールドやAPIエンドポイントフィールドが、ユーザーにメールアドレスの入力を要求する場合、サービスはユーザーの入力が実際に有効なメールアドレスであることを検証すべきです。会社は、入力バリデーションの品質が低いと文句を言う外部ユーザーに、より注意を払う可能性があります。彼らは会社の製品の使用や支払いをやめるかもしれないからです。選択肢のあまりない内部ユーザーからの同様のフィードバックは無視されるかもしれません。

エラーが発生したとき、高品質なサービスは、サポート担当者やサービスの開発者に連絡するという時間のかかるプロセスを必要とせず、ユーザーがエラーを修正する方法を案内する有益なエラーメッセージを返すべきです。外部サービスは、より良いエラーメッセージを提供したり、より多くのリソースとインセンティブを高品質なサポートに割り当てたりすることがあります。

顧客がメッセージを送れば、数分または数時間で返信を受け取ることがありますが、従業員の質問に応答するには数時間や数日かかる場合があります。社内ヘルプデスクチャネルへの質問にまったく応答がないこともあります。従業員への返答が、よくないドキュメントを示すだけということもあります。

組織が十分なリソースとインセンティブを提供する場合にのみ、内部サービスは外部サービスと同程度の品質に達することができます。より良いユーザー体験とサポートはユーザーの士気と生産性を向上させるので、組織は内部ユーザーがどれだけよく対応されているかを測定するメトリクスの設定を検討してもよいでしょう。これらの複雑さを避ける方法の一つはクラウドサービスを使うことです。これらの考察は外部対内部サービス全般に一般化できます。

最後に、個々の開発者は自分自身に高い基準を持つべき責任がありますが、他者の仕事の品質について仮定をすべきではありません。とはいえ、内部依存関係の品質が常に低いと、組織の生産性と士気を損なうおそれがあります。

アップグレード

組織のベアメタルインフラで使用されるハードウェアおよびソフトウェア技術は、古くなり、アップグレードが難しくなります。これはメインフレームを使用する金融企業にとって明らかです。メインフレームからコモディティサーバーへの切り替えは非常に高価で、難しく、リスクが高いため、こうした企業は同等の処理能力をコモディティサーバーで揃えるよりはるかに高価な新しいメインフレームを買い続けます。コモディティサーバーを使用する組織もまた、ハードウェアとソフトウェアを常にアップグレードするための専門知識と労力が必要です。例えば、大規模な組織で使用されるMySQLのバージョンをアップグレードするだけでも、かなりの時間と労力がかかります。多くの組織は、そのような保守をクラウドプロバイダーにアウトソースすることを好みます。

いくつかの欠点

クラウドプロバイダーの欠点の一つはベンダーロックインです。アプリの一部またはすべてのコンポーネントを別のクラウドベンダーに移行することにした場合、このプロセスは単純ではないかもしれません。あるクラウドプロバイダーから別のプロバイダーへデータとサービスを移行するために多大なエンジニアリング工数が必要になり、この移行期間中は重複したサービス料金を支払う必要があるかもしれません。

ベンダーから移行したくなる理由は多数あります。今日、ベンダーは競争力のある価格で厳しいSLAを満たすよく管理された会社かもしれませんが、これが常に真であるという保証はありません。会社のサービス品質が将来悪化し、SLAを満たせなくなることもあります。価格が競争力を失い、ベアメタルや他のクラウドベンダーの方が将来安くなる可能性もあります。あるいはベンダーがセキュリティや他の望ましい特性を欠いていることが判明することもあります。

もう一つの欠点は、データとサービスのプライバシー・セキュリティに対するオーナーシップの欠如です。クラウドプロバイダーがデータを保護してくれる、またはサービスのセキュリティを確保してくれることを信頼できないかもしれません。ベアメタルでは、プライバシーとセキュリティを自分で確認できます。

これらの理由から、多くの企業はマルチクラウド戦略を採用し、単一のクラウドベンダーではなく複数のクラウドベンダーを使用しています。これにより、必要が突然生じた場合に短期間でいずれかのベンダーから移行できるようにしているのです。

1.4.10 サーバーレス: Function as a Service (FaaS)

特定のエンドポイントや関数が頻繁に使われない、または厳しいレイテンシ要件がない場合、AWS LambdaやAzure Functionsのような Function as a Service (FaaS) プラットフォーム上で関数として実装する方が安価かもしれません。必要なときにだけ関数を実行することで、リクエストを継続的に待つホストを用意する必要がなくなります。

OpenFaaSとKnativeはオープンソースのFaaSソリューションで、自前のクラスタ上でFaaSをサポートしたり、AWS Lambda上のレイヤーとして使って、クラウドプラットフォーム間で関数の可搬性を向上させたりできます。本書執筆時点では、オープンソースのFaaSソリューションと、Azure Functionsなどの他のベンダー管理FaaSとの間に統合はありません。

Lambda関数のタイムアウトは15分です。FaaSはこの時間内に完了できるリクエストを処理することを目的としています。

典型的な構成では、APIゲートウェイサービスが受信リクエストを受け取り、対応するFaaS関数をトリガーします。APIゲートウェイは、リクエストを待ち続ける継続的に実行されるサービスが必要なため、不可欠です。

FaaSのもう一つの利点は、サービス開発者がデプロイメントやスケーリングを管理する必要がなく、ビジネスロジックのコーディングに集中できる点です。

FaaS関数の1回の実行には、Dockerコンテナの起動、適切な言語ランタイム（Java、Python、Node.jsなど）の起動と関数の実行、ランタイムとDockerコンテナの終了といった手順が必要となります。これは一般にコールドスタートと呼ばれます。起動に数分かかるフレームワーク（特定のJavaフレームワークなど）はFaaSに不向きかもしれません。これがGraalVM（https://www.graalvm.org/）のような、高速な起動と低メモリフットプリントを持つJDKの開発を促しました。

なぜこのオーバーヘッドが必要なのでしょうか? なぜすべての関数を単一のパッケージにパッケージ化し、モノリスのようにすべてのホストインスタンスで実行できないのでしょうか? その理由はモノリスの欠点にあります（付録Aを参照）。

なぜ頻繁に使われる関数を一定時間（つまり有効期限付きで）特定のホストにデプロイしないのでしょうか? そのようなシステムはオートスケールするマイクロサービスと似ており、起動に時間のかかるフレームワークを使用する際に検討できます。

FaaSの可搬性は議論の余地があります。一見すると、AWS Lambdaのような独自のFaaSで多くの作業を行ってきた組織はロックインされる可能性があります。別のソリューションへの移行は困難で、時間とコストがかかります。オープンソースのFaaSプラットフォームは完全な解決策にはなりません。なぜなら、自前のホストをプロビジョニングして保守する必要があり、それはFaaSのスケーラビリティの目的を損ねるからです。この問題は規模が大きくなったとき特に大きくなり、FaaSがベアメタルよりはるかに高価になる可能性があります。

しかし、FaaSの関数は2つの層で書くことができます: 関数の主要なロジックを含む内側の層/関数を、ベンダー固有の設定を含む外側の層/関数でラップする方式です。任意の関数のベンダーを切り替えるには、外側の関数のみ変更すればよいだけです。

Spring Cloud Function（https://spring.io/projects/spring-cloud-function）はこの概念を一般化した新興のFaaSフレームワークです。AWS Lambda、Azure Functions、Google Cloud Functions、Alibaba Function Computeでサポートされており、将来は他のFaaSベンダーでもサポートされるかもしれません。

1.4.11 結論: バックエンドサービスのスケーリング

パート1の残りでは、バックエンドサービスをスケーリングするための概念と技術について議論します。フロントエンド/UIサービスは通常Node.jsサービスで、行うことはReactJSやVue.jsなどのJavaScriptフレームワークで書かれた同じブラウザアプリをどのユーザーにも提供することだけなので、クラスタサイズの調整とGeoDNSの使用によって単純にスケールできます。バックエンドサービスは動的で、各リクエストに異なるレスポンスを返すことができます。そのスケーラビリティ技術はより多様で複雑です。前述の例では機能的パーティショニングについて議論しました。必要に応じて時折触れていきます。

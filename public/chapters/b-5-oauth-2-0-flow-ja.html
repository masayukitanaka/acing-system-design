B.5.1 OAuth 2.0の用語

  • リソースオーナー（Resource owner）―データを所有するか、アプリケーションがリクエストする特定の操作を制御するユーザー。たとえば、Googleアカウントに連絡先がある場合、あなたはそのデータのリソースオーナーです。そのデータへのアクセス権限をアプリケーションに付与できます。本節では、簡潔のためリソースオーナーをユーザーと呼びます。
  • クライアント（Client）―リソースをリクエストするアプリケーション。
  • 認可サーバ（Authorization server）―ユーザーが権限を認可するために使うシステム。accounts.google.comなど。
  • リソースサーバ（Resource server）―クライアントが欲しいデータを保持するシステムのAPI。Google Contacts APIなど。システムによっては、認可サーバとリソースサーバは同じか別個のシステムであり得ます。
  • 認可付与（Authorization grant）―リソースへのアクセスに必要な権限へのユーザーの同意の証明。
  • リダイレクトURI、コールバックとも呼ばれる―認可サーバがクライアントにリダイレクトして戻るときのURIまたは宛先。
  • アクセストークン（Access token）―クライアントが認可されたリソースを取得するために使うキー。
  • スコープ（Scope）―認可サーバは理解するスコープのリストを持ちます（たとえば、ユーザーのGoogle連絡先リストの読み取り、メールの読み取り、メールの削除など）。クライアントは必要なリソースに応じて特定のスコープセットを要求できます。

B.5.2 クライアントの初期セットアップ

（MintやYelpのような）アプリは、クライアントになってユーザーがOAuthを使えるようにするため、認可サーバ（Googleなど）と一度きりのセットアップを行う必要があります。MintがGoogleにクライアント作成を依頼すると、Googleは次を提供します。

  • クライアントID。通常は長い一意の文字列識別子。フロントチャネルでの初期リクエストとともに渡されます。
  • クライアントシークレット。トークン交換中に使われます。

1. ユーザーから認可を得る

フローは（Google）リソースオーナーがクライアントアプリ（Yelp）上にいることから始まります。YelpはユーザーがGoogleアカウントの特定データへのアクセスを付与するためのボタンを表示します。そのボタンをクリックすると、ユーザーはOAuthフロー―アプリケーションが認可を得て要求された情報のみにアクセスできるようになる一連のステップ―を通過することになります。

ユーザーがボタンをクリックすると、ブラウザは認可サーバ（accounts.google.comになり得るGoogleドメインや、FacebookやOktaの認可サーバなど）にリダイレクトされます。ここで、ユーザーはログイン（つまりメールとパスワードを入力してLoginをクリック）するよう求められます。ブラウザのナビゲーションバーでGoogleドメインにいることを確認できます。これはセキュリティ向上で、ユーザーはMintやYelpのような他のアプリではなくGoogleにメールとパスワードを提供します。

このリダイレクトで、クライアントは「https://accounts.google.com/o/oauth2/v2/auth?client_id=yelp&redirect_uri=https%3A%2F%2Foidcdebugger.com%2Fdebug&scope=openid&response_type=code&response_mode=query&state=foobar&nonce=uwtukpm946m」のようなURLを伴うクエリで認可サーバに設定情報を渡します。クエリパラメータは：

  • client_id―クライアントを認可サーバに識別します。たとえば、Yelpがクライアントであることをグーグルに伝えます。
  • redirect_uri（コールバックURIとも呼ばれる）―リダイレクトURI。
  • scope―要求されたスコープのリスト。
  • response_type―クライアントが欲しい認可付与のタイプ。いくつかの異なるタイプがあり、まもなく説明します。ここでは、最も一般的なタイプである認可コード付与（authorization code grant）を仮定します。これは認可サーバへのコードのリクエストです。
  • state―stateはクライアントからコールバックへ渡されます。後述するステップ4で議論するように、これによりクロスサイトリクエストフォージェリ（CSRF）攻撃を防ぎます。
  • nonce―「number used once」の略。リプレイ攻撃（本書の範囲外）を防ぐためにリクエストを一意にラベル付けするために使われる、サーバが提供するランダム値。

2. ユーザーがクライアントのスコープに同意

ログイン後、認可サーバはクライアントが要求するスコープリストに同意するようユーザーに求めます。本例では、Googleは他のアプリが要求するリソースのリスト（公開プロフィールや連絡先リストなど）を提示し、それらのリソースをそのアプリに付与することに同意するかの確認を求めるプロンプトを提示します。これにより、ユーザーが意図しないリソースへのアクセスを誤って付与することを防ぎます。

「いいえ」または「はい」をクリックしたかに関わらず、ブラウザはユーザーの判断に応じて異なるクエリパラメータでアプリのコールバックURIにリダイレクトされます。「いいえ」をクリックすると、アプリはアクセスを付与されません。リダイレクトURIは「https://yelp.com/callback?error=access_denied&error_description=The user did not consent.」のようなものになり得ます。「はい」をクリックすると、アプリはGoogle Contacts APIのようなGoogle APIからユーザーが付与したリソースをリクエストできます。認可サーバは認可コードを伴うリダイレクトURIにリダイレクトします。リダイレクトURIはhttps://yelp.com/callback?code=3mPDQbnIOyseerTTKPV&state=foobarのようなものになり、クエリパラメータ「code」が認可コードです。

3. アクセストークンをリクエスト

クライアントは、（クライアントと認可サーバだけが知る）クライアントの秘密鍵を含むPOSTリクエストを認可サーバに送信して、認可コードをアクセストークンと交換します。例：

POST www.googleapis.com/oauth2/v4/token

Content-Type: application/x-www-form-urlencoded

code=3mPDQbnIOyseerTTKPV&client_id=yelp&client_secret=secret123&grant_type=authorization_code

認可サーバはコードを検証し、クライアントから受け取ったstateとともにアクセストークンで応答します。

4. リソースをリクエスト

CSRF攻撃を防ぐため、クライアントはサーバに送信したstateがレスポンス内のstateと同一であることを検証します。次に、クライアントはアクセストークンを使ってリソースサーバから認可されたリソースをリクエストします。アクセストークンは、クライアントが要求されたスコープのみ（たとえばユーザーのGoogle連絡先への読み取り専用アクセス）にアクセスすることを許します。スコープ外や他のスコープのリソースへのリクエストは拒否されます（たとえば連絡先の削除やユーザーの位置履歴へのアクセス）。

ET api.google.com/some/endpoint

Authorization: Bearer h9pyFgK62w1QZDox0d0WZg

B.5.3 バックチャネルとフロントチャネル

なぜ認可コードを取得してからアクセストークンと交換するのか？認可コードをそのまま使うか、すぐにアクセストークンを取得すればいいのではないか？

ネットワークセキュリティの用語であるバックチャネルとフロントチャネルの概念を導入します。

フロントチャネル通信（Front-channel communication）は、プロトコル内で観測可能な2者以上の通信です。バックチャネル通信（Back-channel communication）は、プロトコル内の少なくとも1者にとって観測不可能な通信です。これによりバックチャネルはフロントチャネルよりセキュアになります。

バックチャネルや高度にセキュアなチャネルの例は、クライアントのサーバからGoogle APIサーバへのSSL暗号化されたHTTPリクエストです。フロントチャネルの例はユーザーのブラウザです。ブラウザはセキュアですが、ブラウザからデータが漏れる可能性のある抜け穴や場所があります。Webアプリケーションに秘密のパスワードやキーがあり、それをWebアプリのHTMLやJavaScriptに入れた場合、このシークレットはページソースを表示する人に見えてしまいます。攻撃者はネットワークコンソールやChrome Developer Toolsを開いてJavaScriptを表示・変更することもできます。ブラウザは完全に信頼していないのでフロントチャネルとみなされますが、バックエンドサーバで動作するコードは完全に信頼しています。

クライアントが認可サーバへ向かう状況を考えます。これはフロントチャネルで起こっています。フルページのリダイレクト、送信リクエスト、認可サーバへのリダイレクト、認可サーバへのリクエストの内容はすべてブラウザを通って渡されます。認可コードもブラウザ（つまりフロントチャネル）を通って送信されます。この認可コードが悪意のあるツールバーやブラウザリクエストをログ記録できるメカニズムによって傍受されたとしても、トークン交換はバックチャネルで行われるので、攻撃者はアクセスコードを取得できません。

トークン交換はブラウザではなくバックエンドと認可チャネルの間で行われます。バックエンドはトークン交換に秘密鍵も含めますが、攻撃者はそれを知りません。この秘密鍵の送信がブラウザ経由なら、攻撃者はそれを盗めます。したがって送信はバックチャネル経由で行われます。

OAuth 2.0フローは、高度にセキュアであることを保証するために、フロントチャネルとバックチャネルの最良の特性を活用するよう設計されています。フロントチャネルはユーザーとのやり取りに使われます。ブラウザはユーザーに直接対話してログイン画面と同意画面を提示するためのものなので、これらの画面を提示します。秘密鍵をブラウザに完全に信頼することはできないので、フローの最後のステップ（つまり交換）は信頼するシステムであるバックチャネルで行われます。

認可サーバはまた、アクセストークンが期限切れの場合に、ユーザーとやり取りすることなくクライアントが新しいアクセストークンを取得できるよう、リフレッシュトークンを発行することもできます。これは本書の範囲外です。

重み付きトライジェネレータは、日次バッチETLパイプライン（リアルタイム更新が必要ならストリーミングパイプライン）にできます。パイプラインには単語処理ETLジョブが含まれます。図11.2では、単語処理ETLジョブと重み付きトライジェネレータが別のパイプラインステージになっています。これは、単語処理ETLジョブが他の多くの目的やサービスにも有用であり得るため、また別ステージにすることで実装・テスト・保守・スケールを独立に行えるためです。

単語カウントパイプラインには、図11.4にDAGとして示す次のタスク／ステップを持たせ得ます。

  1. ロギングサービスの検索トピック（および必要なら他のトピック）から関連ログを取得して一時ストレージに置く。
  2. 検索文字列を単語に分割する。
  3. 不適切な単語を除外する。
  4. 単語をカウントしてword countテーブルに書き込む。必要な正確性に応じて、すべての単語をカウントするか、count-min sketch（17.7.1節を参照）のような近似アルゴリズムを使う。
  5. 適切な単語でフィルタし、未知の人気語を記録する。
  6. word countテーブルから重み付きトライを生成する。
  7. 重み付きトライをバックエンドホストへ送信する。

図11.4 単語カウントパイプラインのDAG。未知の人気語の記録と適切な単語のフィルタリングは独立に行える。

生検索ログにはさまざまなデータベース技術を検討できます。

  • 典型的なELKスタックの一部である、デフォルト保持期間7日の日別パーティションのElasticsearchインデックス。
  • 各日のログをHDFSファイル（日別パーティション）にする。ユーザー検索は、保持期間を数日（何らかの理由で古いメッセージを見る必要に備えて1日だけではなく）に設定したKafkaトピックに発行できる。各日の決まった時刻に、パイプラインの最初のステージが、設定時刻より新しいタイムスタンプを持つメッセージに到達するまで（つまり1メッセージ余分に消費することになるが、このわずかな不正確さは問題ない）、またはトピックが空になるまでメッセージを消費する。コンシューマはその日付に対応するパーティションの新しいHDFSディレクトリを作成し、そのディレクトリ内の単一ファイルにすべてのメッセージを追記する。各メッセージはタイムスタンプ、ユーザーID、検索文字列を含み得る。HDFSは保持期間を設定する仕組みを持たないため、この選択肢では古いデータを削除するステージをパイプラインに追加する必要がある。
  • SQLは全データが単一ノードに収まる必要があるので実現できない。

ロギングサービスがELKサービスであると仮定しましょう。4.3.5節で述べたように、HDFSはMapReduceプログラミングモデルの一般的なストレージシステムです。MapReduceプログラミングモデルを使って、多数のノードでデータ処理を並列化します。HiveまたはSparkをHDFSと組み合わせて使えます。Hiveを使う場合、Hive on Spark（https://spark.apache.org/docs/latest/sql-data-sources-hive-tables.html）を使えるので、HiveアプローチもSparkアプローチも実際にはSparkを使うことになります。SparkはHDFSから読み書きしてメモリにデータを読み込み、メモリ上でデータを処理できます。これはディスク上での処理より遥かに高速です。以降の節では、Elasticsearch、Hive、Sparkを使った実装を簡単に議論します。コードの徹底的な議論はシステム設計面接の範囲外であり、簡単な議論で十分です。

これは典型的なETLジョブです。各ステージで、前ステージのデータベースストレージから読み取り、データを処理し、次ステージが使うデータベースストレージに書き込みます。

11.7.1 各ステップは独立したタスクであるべき

図11.4のバッチETL DAGをもう一度参照すると、なぜ各ステップが独立したステージなのでしょうか？最初にMVPを開発するときは、重み付きトライ生成を単一のタスクとして実装し、単純にすべての関数を連結することも可能です。このアプローチはシンプルですが、保守性に欠けます。（複雑性と保守性は相関があるように見え、シンプルなシステムは通常保守しやすいですが、ここではトレードオフがある例を見ることになります。）

バグを最小化するために個々の関数に対する徹底的なユニットテストを実装し、本番で遭遇する残存バグを特定するためにロギングを実装し、エラーをスローし得る関数をtry-catchブロックで囲んでこれらのエラーをログ記録できます。それでも特定の問題を見逃す可能性があり、重み付きトライ生成のエラーがプロセスをクラッシュさせると、プロセス全体を最初からやり直す必要があります。これらのETL操作は計算集約的で完了に数時間かかり得るため、こうしたアプローチはパフォーマンスが低くなります。これらのステップを別個のタスクとして実装し、Airflowのようなタスクスケジューラシステムを使うべきです。これにより、各タスクは前のタスクが正常に完了した後にのみ実行されます。

11.7.2 ElasticsearchからHDFSへ関連ログを取得する

Hiveでは、CREATE EXTERNAL TABLEコマンド（https://www.elastic.co/guide/en/elasticsearch/hadoop/current/hive.html#_reading_data_from_elasticsearch）を使って、Elasticsearchトピック上にHiveテーブルを定義できます。次に、INSERT OVERWRITE DIRECTORY '/path/to/output/dir' SELECT * FROM Log WHERE created_at = date_sub(current_date, 1);のようなHiveコマンドでログをHDFSに書き出せます。（このコマンドは前日分のログを取得したいことを前提としています。）

Sparkでは、SparkContextのesRDDメソッド（https://www.elastic.co/guide/en/elasticsearch/hadoop/current/spark.html#spark-read）でElasticsearchトピックに接続し、Sparkのfilterクエリ（https://spark.apache.org/docs/latest/api/sql/index.html#filter）で該当日付のデータを読み取り、SparkのsaveAsTextFile関数（https://spark.apache.org/docs/latest/api/scala/org/apache/spark/api/java/JavaRDD.html#saveAsTextFile(path:String):Unit）でHDFSに書き込めます。

面接で、HiveやSparkがElasticsearchとの統合を持っているか知らなくても、これらが人気の主流データプラットフォームなので統合は存在しそうだと面接官に伝えられます。統合が存在しない場合や、面接官から求められた場合は、片方のプラットフォームから読み取って他方に書き込むスクリプトのコードについて簡単に議論できます。このスクリプトは各プラットフォームの並列処理機能を活用すべきです。パーティショニング戦略も議論できます。このステップでは、入力／ログはサービスでパーティション化されているかもしれず、出力は日付でパーティション化されます。このステージでは、検索文字列の両端の空白を除去することもできます。

11.7.3 検索文字列を単語に分割し、その他のシンプルな操作を行う

次に、split関数で検索文字列を空白で分割します。（ユーザーが空白を省略する（例：「HelloWorld」）、ピリオド・ダッシュ・カンマなど他の区切り文字を使う、といった一般的な問題も考慮する必要があるかもしれません。本章ではこれらの問題は稀であると仮定し、無視できます。これらの問題が実際にどれだけ一般的かを見つけるために、検索ログの分析を行いたい場合もあるでしょう。）これら分割された文字列を「検索語」と呼びます。Hiveのsplit関数についてはhttps://cwiki.apache.org/confluence/display/Hive/LanguageManual+UDF#LanguageManualUDF-StringFunctions、Sparkのsplit関数についてはhttps://spark.apache.org/docs/latest/api/sql/index.html#splitを参照してください。前ステップのHDFSファイルから読み取り、文字列を分割します。

このステージでは、システムの寿命にわたって変わる可能性が低いさまざまなシンプルな操作も実行できます。たとえば、6文字以上の長さで文字のみを含む（数字や特殊文字を含まない）文字列でフィルタしたり、これ以降の処理で大文字小文字を考慮しなくて済むようすべての文字列を小文字化したりします。その後、これらの文字列を別のHDFSファイルに書き込みます。

11.7.4 不適切な単語を除外する

適切な単語でフィルタする、もしくは不適切な単語を除外するときには、次の2つの部分を考えます。

  1. 適切な単語と不適切な単語のリストを管理する。
  2. 検索語のリストを適切な単語と不適切な単語のリストに対してフィルタする。

Wordsサービス

Wordsサービスは適切な単語または不適切な単語のソート済みリストを返すAPIエンドポイントを持ちます。これらのリストは最大でも数MBで、二分探索が可能なようにソートされています。サイズが小さいため、リストを取得するホストはWordsサービスが利用不可になった場合に備えてリストをメモリにキャッシュできます。それでも、Wordsサービスには3.3.2節で議論したように、ステートレスなUIサービスとバックエンドサービス、レプリケーションされたSQLサービスから成る典型的な水平スケールアーキテクチャを使えます。図11.5はWordsサービスの高レベルアーキテクチャを示しています。これはSQLデータベースとの間で単語の読み書きを行うシンプルなアプリケーションです。適切な単語と不適切な単語のSQLテーブルは、単語用の文字列列、単語がテーブルに追加された時刻のタイムスタンプ、追加したユーザー、なぜその単語が適切／不適切なのかというノートのための任意の文字列列など、情報を提供する他の列を含み得ます。Wordsサービスは、管理者ユーザーが適切な単語と不適切な単語のリストを閲覧し、手動で単語を追加・削除できるUI（これらはすべてAPIエンドポイント）を提供します。バックエンドはカテゴリで単語をフィルタするエンドポイントや、単語を検索するエンドポイントも提供できます。

図11.5 Wordsサービスの高レベルアーキテクチャ

不適切な単語のフィルタリング

単語カウントETLパイプラインはWordsサービスに不適切な単語をリクエストし、このリストをHDFSファイルに書き込みます。以前のリクエストからすでにHDFSファイルがあるかもしれません。Wordsサービスの管理者がそれ以降に特定の単語を削除している可能性があるため、新しいリストは古いHDFSファイルに存在する単語を持っていない可能性があります。HDFSは追記専用なので、HDFSファイルから個別の単語を削除することはできず、代わりに古いファイルを削除して新しいファイルを書く必要があります。

不適切な単語のHDFSファイルがあれば、LOAD DATAコマンドでこのファイルにHiveテーブルを登録し、次のようなシンプルなクエリで不適切な単語をフィルタアウトして、出力を別のHDFSファイルに書き込めます。

Sparkのような分散分析エンジンを使って、どの検索文字列が不適切な単語かを判定できます。PySparkやScalaでコーディングするか、Spark SQLクエリでユーザーの単語と適切な単語をJOINできます。

面接では、SQLクエリに費やすのは30秒未満にして、重要なロジックを次のように書き留めるべきです。50分を上手に使いたいので、完璧なSQLクエリを書くために貴重な数分を費やしたくない、と簡単に説明できます。これはシステム設計面接の範囲外であり、SQLのスキルを披露する場ではないことに、面接官はおそらく同意して先へ進めさせてくれるでしょう。データエンジニアのポジションの面接の場合は例外かもしれません。

  • WHERE句のようなフィルタ
  • JOIN条件
  • AVG、COUNT、DISTINCT、MAX、MIN、PERCENTILE、RANK、ROW_NUMBERなどの集約

SELECT word FROM words WHERE word NOT IN (SELECT word from inappropriate_words);

不適切な単語テーブルは小さいので、より高速なパフォーマンスのためmap join（MapReduceジョブのマッパーがJOINを実行する。https://cwiki.apache.org/confluence/display/hive/languagemanual+joinsを参照）を使えます。

SELECT /*+ MAPJOIN(i) */ w.word FROM words w LEFT OUTER JOIN inappropriate_words i ON i.word = w.word WHERE i.word IS NULL;

ブロードキャストハッシュJOIN（Broadcast hash join）はSparkにおけるHiveのmap joinに相当します。ブロードキャストハッシュJOINは、各ノードのメモリに収まる小さな変数またはテーブル（Sparkではspark.sql.autoBroadcastJoinThresholdプロパティで設定され、デフォルトは10 MB）と、ノード間で分割が必要な大きなテーブルとの間で行われます。ブロードキャストハッシュJOINは次のように行われます。

  1. 小さいテーブルにハッシュテーブルを作成する。キーはJOINされる値で、値は行全体。たとえば、今の状況では単語の文字列でJOINするので、（“word”、“created_at”、“created_by”）の列を持つinappropriate_wordsテーブルのハッシュテーブルには、{(“apple”, (“apple”, 1660245908, “brad”)), (“banana”, (“banana”, 1550245908, “grace”)), (“orange”, (“orange”, 1620245107, “angelina”)) . . . }のようなエントリが含まれ得る。
  2. JOIN操作を実行するすべてのノードにこのハッシュテーブルをブロードキャスト／コピーする。
  3. 各ノードは小さいテーブルを、そのノードに割り当てられた大きなテーブルの部分にJOINする。

両方のテーブルがメモリに収まらない場合は、シャッフルソートマージJOIN（shuffled sort merge join）が行われます。両方のデータセットがシャッフルされ、レコードはキーでソートされ、両側を反復してJOINキーに基づいてJOINするマージJOINが行われます。このアプローチは、不適切な単語に関する統計を保持する必要がないと仮定しています。SparkのJOINのさらなる学習リソースは次のとおりです。

  • https://spark.apache.org/docs/3.3.0/sql-performance-tuning.html#join-strategy-hints-for-sql-queries またはhttps://spark.apache.org/docs/3.3.0/rdd-programming-guide.html#broadcast-variables。JOINのパフォーマンスを改善するさまざまなSpark JOIN戦略についての公式Sparkドキュメント。利用可能なJOIN戦略を列挙していますが、詳細な仕組みは議論していません。徹底的な議論は下のリソースを参照してください。
  • https://spark.apache.org/docs/3.3.0/sql-performance-tuning.html#join-strategy-hints-for-sql-queries
  • Damiji, J. et al. A Family of Spark Joins. Learning Spark, 2nd Edition. O'Reilly Media, 2020.
  • Chambers, B. and Zaharia, M. Joins. Spark: The Definitive Guide: Big Data Processing Made Simple. O'Reilly Media, 2018.
  • https://docs.qubole.com/en/latest/user-guide/engines/hive/hive-mapjoin-options.html
  • https://towardsdatascience.com/strategies-of-spark-join-c0e7b4572bcf

11.7.5 ファジーマッチングとスペル訂正

単語をカウントする前の最後の処理ステップは、ユーザーの検索語の誤字を訂正することです。文字列を受け取り、ファジーマッチングアルゴリズムを持つライブラリで誤字の可能性を訂正し、元の文字列またはファジーマッチした文字列を返す関数をコーディングできます。（ファジーマッチング、別名近似文字列マッチングは、パターンに近似的にマッチする文字列を見つける手法です。ファジーマッチングアルゴリズムの概要は本書の範囲外です。）この関数をSparkで均等サイズのサブリストに分割した単語リストに対して並列実行し、出力をHDFSに書き込めます。

このスペル訂正ステップを独立したタスク／ステージにするのは、複数のファジーマッチングアルゴリズムやライブラリ／サービスから選択できるため、要件に合わせて特定のアルゴリズムを選ぶことがあるからです。このステージを別にしておけば、ファジーマッチング用のライブラリやサービスを容易に切り替えられ、このパイプラインステージへの変更が他ステージに影響しません。ライブラリを使う場合、変化するトレンドや人気の新語に追従するためにライブラリを更新する必要があり得ます。

11.7.6 単語をカウントする

これで単語のカウントの準備ができました。これは素直なMapReduce操作にもできますし、count-min sketch（17.7.1節を参照）のようなアルゴリズムを使うこともできます。

以下のScalaコードはMapReduceアプローチを実装したものです。このコードはhttps://spark.apache.org/examples.htmlからわずかに修正したものです。入力HDFSファイルの単語をcountsという（String, Int）ペアにマップし、カウントの降順でソートして別のHDFSファイルとして保存します。

val textFile = sc.textFile("hdfs://...")

val counts = textFile.map(word => (word, 1)).reduceByKey(_ + _).map(item => item.swap).sortByKey(false).map(item => item.swap)

counts.saveAsTextFile("hdfs://...")

11.7.7 適切な単語でフィルタする

単語カウントステップは、フィルタすべき単語数を大幅に削減するはずです。適切な単語でのフィルタリングは、11.7.4節の不適切な単語のフィルタリングと非常に似ています。

適切な単語でフィルタするにはSELECT word FROM counted_words WHERE word IN (SELECT word FROM appropriate_words);のようなシンプルなHiveコマンド、もしくはSELECT /*+ MAPJOIN(a) */ c.word FROM counted_words c JOIN appropriate_words a on c.word = a.word;のようなMap Joinまたはブロードキャストハッシュ結合を使えます。

11.7.8 新しい人気の未知語の管理

前ステップで単語をカウントした後、これまで知らなかった人気の新語が上位100に見つかるかもしれません。このステージでは、これらの語をWordsサービスに書き込み、Wordsサービスがそれをunknown_wordsというSQLテーブルに書き込めます。11.7.4節と同様に、Wordsサービスは運用スタッフがこれらの単語を適切な単語または不適切な単語のリストに手動で追加できるよう、UI機能とバックエンドエンドポイントを提供します。

図11.4の単語カウントバッチETLジョブDAGに示すように、このステップは適切な単語のフィルタリングと並列に独立して実行できます。

11.7.9 重み付きトライの生成と配信

これで重み付きトライを構築するための適切な上位語のリストが得られました。このリストは数MBに過ぎないため、重み付きトライは単一ホスト上で生成できます。重み付きトライを構築するアルゴリズムはシステム設計面接の範囲外です。コーディング面接の問題になり得ます。部分的なScalaクラス定義は次のようになりますが、バックエンドの言語でコーディングします。

class TrieNode(var children: Array[TrieNode], var weight: Int) {

  // Functions for  

  // - create and return a Trie node.

  // - insert a node into the Trie.

  // - getting the child with the highest weight.

}

重み付きトライをJSONにシリアライズします。トライのサイズは数MBで、検索バーがユーザーに表示されるたびにクライアントへダウンロードするには大きすぎるかもしれませんが、すべてのホストにレプリケートするには十分小さいサイズです。トライはAWS S3のような共有オブジェクトストアや、MongoDBやAmazon DocumentDBのようなドキュメントデータベースに書き込めます。バックエンドホストは毎日オブジェクトストアにクエリして更新されたJSON文字列を取得するように設定できます。ホストはランダムな時刻にクエリすることもできますし、同時リクエストが多数発生してオブジェクトストアを圧倒するのを防ぐため、ジッターを加えて同じ時刻にクエリするように設定することもできます。

共有オブジェクトが大きい（たとえばギガバイト級の）場合、CDNへの配置を検討すべきです。このトライが小さいことのもう1つの利点は、ユーザーが検索アプリをロードしたときにトライ全体をダウンロードできることです。これにより、トライのルックアップがサーバ側ではなくクライアント側で行えます。これによりバックエンドへのリクエスト数が大幅に減り、次のような利点があります。

  • ネットワークが信頼できなかったり遅かったりすると、検索文字列入力中に時々候補が表示されない可能性があり、ユーザー体験が悪くなる。
  • トライが更新されたとき、検索文字列を入力中のユーザーが変化に気付くかもしれない。たとえば、古いトライの文字列に何らかの関連があった場合、新しいトライにはその関連がなく、ユーザーがその急な変化に気付くこともあります。あるいはユーザーが数文字バックスペースすると、候補が以前と異なることに気付くかもしれません。

地理的に分散したユーザーベースを持つ場合、高パフォーマンスという要件を考えるとネットワークレイテンシは許容できなくなります。複数のデータセンターにホストをプロビジョニングすることもできますが、コストが高く、レプリケーション遅延も発生します。CDNはコスト効率の良い選択肢です。

オートコンプリートサービスは重み付きトライを更新するPUTエンドポイントを提供すべきで、このステージがそれを使って生成した重み付きトライをオートコンプリートサービスに配信します。

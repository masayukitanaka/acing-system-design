バッチジョブは完了に何時間もかかり得、これがすべての区間のロールアップに影響します。たとえば、直近の時間ごとのロールアップジョブのHiveクエリの完了に30分かかると、それ以降のロールアップとその拡張でTop Kリストが利用できなくなります。

  • その時間のTop Kリスト。
  • その時間を含む日のTop Kリスト。
  • その日を含む週と月のTop Kリスト。

ストリーミングパイプラインの目的は、バッチパイプラインがまだ提供していないカウント（とTop Kリスト）を提供することです。ストリーミングパイプラインはこれらのカウントをバッチパイプラインよりはるかに高速に計算する必要があり、近似手法を使うこともできます。

初期集約の後、次のステップは最終カウントを計算して降順でソートすることで、これによりTop Kリストが得られます。本節では、まず単一ホストでのアプローチを考え、それを水平スケール可能にする方法を見つけることでこの問題に取り組みます。

17.6.1 単一ホストでのハッシュテーブルとmax-heap

最初の試みは、ハッシュテーブルを使い、サイズKのmax-heapで頻度カウントによってソートすることです。リスト17.1はこのアプローチでのTop K Golang関数のサンプルです。

リスト17.1 Top Kリストを計算するGolang関数のサンプル

type HeavyHitter struct {

  identifier string

  frequency int

}

func topK(events []String, int k) (HeavyHitter) {

  frequencyTable := make(map[string]int)

  for _, event := range events {

    value := frequencyTable[event]

    if value == 0 {

      frequencyTable[event] = 1

    } else {

      frequencyTable[event] = value + 1

    }

  }

  pq = make(PriorityQueue, k)

  i := 0

  for key, element := range frequencyTable {

    pq[i++] = &HeavyHitter{

      identifier: key,

      frequency: element

    }

    if pq.Len() > k {

      pq.Pop(&pq).(*HeavyHitter)

    }

  }

  /*  

   * Write the heap contents to your destination.

   * Here we just return them in an array.

   */

  var result [k]HeavyHitter

  i := 0

  for pq.Len() > 0 {

    result[i++] = pq.Pop(&pq).(*HeavyHitter)

  }

  return result

}

本システムでは、さまざまな時間バケット（時間、日、週、月、年）に対してこの関数の複数のインスタンスを並列で実行できます。各期間の終わりに、max-heapの内容を保存し、カウントを0にリセットし、新しい期間のカウントを開始できます。

集約

製品IDとタイムスタンプの組み合わせで集約することに注目してください。読み進める前に、なぜかを考えてみてください。

なぜ製品IDとタイムスタンプの組み合わせで集約するのか？Top Kリストは開始時刻と終了時刻を持つ期間を持つからです。各販売イベントが正しい時間範囲で集約されることを保証する必要があります。たとえば、2023-01-01 10:08 UTCに発生した販売イベントは次に集約されるべきです。

  1. [2023-01-01 10:08 UTC, 2023-01-01 11:00 UTC)の時間範囲。
  2. [2023-01-01, 2023-01-02)の日範囲。
  3. [2022-12-28 00:00 UTC, 2023-01-05 00:00 UTC)の週範囲。2022-12-28と2023-01-05は両方とも月曜日です。
  4. [2023-01-01, 2013-02-01)の月範囲。
  5. [2023, 2024)の年範囲。

アプローチは、最小の期間（つまり時間）で集約することです。任意のイベントがクラスタ内のすべての層を通過するのに数秒しかかからないと想定されるので、クラスタ内のキーが1時間以上古くなることはまずありません。各製品IDは独自のキーを持ちます。各キーに時間範囲を付加しても、キー数が製品ID数の2倍を超えることはなさそうです。

期間の終了から1分後―たとえば[2023-01-01 10:08 UTC, 2023-01-01 11:00 UTC)に対して2023-01-01 11:01 UTC、または[2023-01-01, 2023-01-02)に対して2023-01-02 00:01 UTCに―最終層のそれぞれのホスト（最終ホストと呼べる）はそのヒープをSQLのspeed_tableに書き込めて、ダッシュボードはこの期間の対応するTop Kリストを表示する準備が整います。たまにイベントがすべての層を通過するのに1分以上かかることがあり、その場合最終ホストは更新されたヒープを単にspeed_tableに書き込めます。最終ホストが古い集約キーを保持する保持期間を数時間または数日に設定でき、その後それらを削除できます。

1分待つ代わりに、イベントがホストを通過する際に追跡するシステムを実装し、すべての関連イベントが最終ホストに到達した後にのみ最終ホストがそのヒープをspeed_tableに書き込むようトリガーすることもできます。ただし、これは過度に複雑かもしれず、また、すべてのイベントが完全に処理される前にダッシュボードが近似を表示するのも防いでしまいます。
